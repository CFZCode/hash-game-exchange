# Layout shell, light theme, sidebar and the icon sprites

Part of the bc.game rebuild notes. Index and cross-cutting rules: [../CLAUDE.md](../CLAUDE.md).

## Layout shell

`main.jsx` → `App.jsx` → `MainLayout`. `MainLayout` owns the signals the original's root owns — `sidebarExpanded`, `mobileMenuOpen`, `exploreOpen` and the right-hand drawer — and composes the chrome, each piece of which is single-viewport:

- `Header` renders **two entirely separate trees** — a desktop one (`hidden lg:flex`, 60px tall) and a mobile/tablet one (`flex lg:hidden`, `.page-header`). They are not one responsive component; changes must be made in both. Each has its own signed-in variant on top of that.
- `Sidebar` — desktop only (`hidden lg:flex`), fixed under the header.
- `Tabbar` — mobile/tablet only (`lg:hidden`), fixed bottom, 72px.
- `FloatingActions` — the back-to-top and live-support pair in the bottom-right corner, out of `BackToTop-DG8tIEvj.js`. Desktop only for the reason the tabbar is mobile only: `Ol()` mounts it inside a `when: !m.mobile` branch, and on a phone the tabbar already owns that corner. Gated with `lg:flex` rather than a JS test, matching how the rest of this build splits the two layouts. The original also shifts the stack left by 380px while the chat panel is open, via a `MutationObserver` on `body.chat-unfold`; there is no chat panel yet, so that is left out rather than stubbed.
- `main` content — offsets itself with padding to clear the fixed chrome.
- `Explore` and `Notification` are mounted here too and both **portal to `<body>`**, each for its own reason: the Explore overlay is above everything at z-9999 and must not sit inside the layout's stacking or scroll context, and the drawer is `position: fixed` at z-102 with the page's own `margin-inline-end` shifting what would otherwise be its ancestor.

The fixed elements and the content padding are coupled by hand in `MainLayout.css`: header height (56 mobile / 60 desktop), sidebar width (240 expanded / 64 collapsed), tabbar 72. Changing any chrome dimension means updating the matching padding.

**A dialog route renders over the page you came from, and mounting it outside `<Routes>` is only half of that.** `/login/*` and `/deposit` are real paths with no page of their own — the original's router installs them as dialogs and leaves whatever was underneath in place. `App.jsx` matches them on the pathname and mounts them beside the layout, which keeps *a* page mounted; but `<Routes>` still saw `/deposit`, matched nothing and fell to the catch-all, so the deposit dialog opened over **Home** no matter where you clicked Deposit from. The outlet is now driven by the last **non-dialog** location — React Router calls it a background location and normally threads it through `navigate(to, { state })`; it is tracked in `App` instead so that every existing call site keeps working and a pasted URL behaves like a clicked link. Assigned during render rather than in an effect, because the dialog and the page under it have to agree on the first render or the page flashes; the guard is what makes it terminate and also what holds the value. Closing goes back so you land where you opened it, with the one exception of a dialog reached directly, which has no page behind it and falls back to `/`.

**THE CROSS CLOSES THE WHOLE STACK; THE BACK ARROW POPS ONE — and they are the same helper at two depths**, which is what makes the pair unambiguous rather than a guess. `_3()` (the cross) is `Bd(navigate, stacks.list[0], stacks.index(), navDepth())` and `o()` (the arrow) is `Bd(…, stacks.list[index() - 1], 1, …)`, where `Bd` jumps `-min(n, max(r, 0))` in one go and then steps back one at a time until the URL matches its target. So closing from `/user/medals/:id` does **not** land on `/user/profile/:id`: it goes back as far as the stack is deep and leaves you on the page the stack was opened over. `Bd`'s verification loop is not reproduced — it exists for history entries a real router's `navDepth` cannot account for, which the counter below cannot drift the way that can.

**A jump of −N needs N, so the depth is tracked.** It is `stacks.index()`, derived from the same two facts the original has: whether the new location is an overlay route, and the navigation **action** — `useNavigationType()` here, `action: r` off the router context there. The action is not optional: without it a POP counts upward and the back arrow deepens the stack it just popped. Adjusted during render keyed on location identity, the same pattern the background location uses and for the same reason. Replayed over six real sequences (push/push/close, arrow-then-close, arrow-then-push-again, single dialog, close-and-reopen) before it was believed — note the arrow-then-push case is right *because* a PUSH truncates the forward entries, so `[casino, profile, statistics]` at depth 2 is a correct −2.

Sidebar collapse is purely visual: the container width drops to **72px** with `overflow: hidden` and the inner content (`sm:w-[208px]`) is clipped. No markup swaps on collapse.

**The fold is width-driven at 1280**, which was measured on the live site rather than inferred: `side-unfold` with a 240px rail at 1280, `side-fold` with a 72px one at 1279, re-derived on every resize — a rail folded by hand comes back unfolded when the window crosses up. `MainLayout` reads it at mount and on the same resize tick the drawer rule uses, and below the line the page column takes the reclaimed width (first block at x = 88 with a 16px right gutter) rather than staying at its expanded width and centring, which is what this build did until the two were measured side by side.

The `Footer` is mounted here too, outside the 1248px container, and **two things about it are this build's rather than the original's**. Its prose/feedback band — the "Crypto Online Casino" SEO copy beside "Help us improve your experience" — is now **home page only**, gated by an exact-match ALLOWLIST (`BLURB_SHOWN_ON = ['/']`) rather than the `BLURB_HIDDEN_ON` prefix denylist it started as. The inversion is the point: under a denylist every page added later inherited the band and had to opt out by hand, which is why `/deposit-offer` once needed a line of its own. Exact match rather than a prefix because the catch-all renders Home for unbuilt paths while keeping their URL, and the band should not follow it there. And `.footer-bg` carries a **`1rem` top margin** where the original butts the footer straight against the page — **from `sm` up only; below it that margin is now zero**, measured against the live casino page, which leaves 14px between the bets panel and the tabbar where this build was leaving 69. (The other 48 was `pb-12` on the casino page root, dealt with there.) **That change has a far smaller blast radius than it looks**, and the reason is margin collapsing: the footer margin only ever showed where the page contributed less than 16px of its own, so every page carrying a trailing `mb-4`/`mb-6` for exactly this purpose already wins the collapse and does not move at all. What moves is the handful of pages ending in something smaller. The desktop half is untouched because desktop is out of scope for the responsive pass; the original says it should go there too.

Empty files and directories mark the next pieces to build: `src/layouts/GameLayout/`, `src/components/ui/`, `src/styles/`, `src/context/LayoutContext.jsx` and `src/App.css`. An empty file here is a placeholder, not a stub — nothing imports one. `src/layouts/MainLayout/GlobalChat/` is the exception and is not pending: it is a leftover from before the right-hand drawer was shared, and the chat panel it was going to hold is `src/components/Chat/`.


## Light theme

**The build is no longer dark-only.** Anywhere in this file that still says it is, is out of date; the preference survives a reload and the whole palette swaps.

**THERE ARE THREE THEME CONTROLS AND NONE OF THEM OWNS THE STATE** — the sidebar's Dark/Light pair, the account page's on `/user/enter`, and the Display mode row on `/settings/preferences`. Both read `darken` and both write through `setTheme`, so they cannot disagree and either one moves the other. Worth knowing before adding a third: the sidebar's was a local `useState(true)` for a long time, a pill that slid and told nothing, and it went on doing exactly that after the palette landed — a control that looks wired and is not is the failure mode here, not a missing control.

**Nothing in the palette is sampled, inferred or chosen.** The original ships the entire light theme in one block — bare `.app-root` in `index-DxOqNczA.css`, against `.app-root.dark` for the dark one — and `src/index.css` carries it converted from that block's `R G B` triples to hex. **Exactly one value is invented and it is flagged there**: `--card_dark`, which the original declares only inside `.app-root.dark .bonus-scope` and gives no light value at all, so `bg-card_dark` resolves to an invalid substitution in the light theme and the promotions cards would paint nothing.

**THE POLARITY IS INVERTED FROM THE ORIGINAL, DELIBERATELY.** There, light is the base and dark is the override. Here `@theme` already held the dark values — which is what every comment in `index.css` documents and what every page was built against — so light arrives as an `.app-root:not(.dark)` override instead. The alternative was duplicating the dark palette into an explicit `.app-root.dark` block so both sides were written out, and that is worse: two copies of forty-eight colours, where editing `@theme` silently loses to the copy. **One palette in `@theme`, one override block, no value written twice.**

**Why the override beats `@theme` without a specificity argument:** Tailwind v4 emits `@theme` into `@layer theme`, and the override block is unlayered — so it wins outright. That is the cascade hazard below working in our favour for once. It was checked against the built CSS rather than assumed. The utilities themselves never change: `bg-layer4` compiles to `var(--color-layer4)` either way, so redeclaring the property on the `.app-root` element is the whole mechanism and every descendant picks it up by inheritance.

**`.bonus-scope` needs its own light selector and that is a cascade requirement, not tidiness.** The bare `.bonus-scope` block is 0,1,0 and the light palette is 0,2,0, so without `.app-root:not(.dark) .bonus-scope` at 0,3,0 the light theme would beat the scope and the quest and promotions pages would lose their overrides. That is exactly why the original writes its two as `.app-root .bonus-scope` and `.app-root.dark .bonus-scope` rather than as a bare class. Diffed rule by rule, only three tokens differ from the global light values — and `--quarterary` is the interesting one: 105 112 114, **identical to the dark scope's**, so that single token is the same colour in both themes while the global one it overrides moves.

**`dark:` KEYS OFF THE CLASS NOW** — `@custom-variant dark (&:where(.dark, .dark *))` at the top of `index.css`. This closed a latent bug as much as it enabled the theme: the stock variant is `prefers-color-scheme`, so every `dark:` utility in the project was silently keyed to the visitor's OS, and the files carrying unguarded pairs rendered their LIGHT arm on a dark page for anyone on a light machine. `:where()` keeps the variant at zero added specificity so a dark arm does not start outranking utilities written after it.

**The state is `theme`, the boolean is `darken`, and they cannot disagree.** `nl` in `index-BsFv7ByC.js` declares the store whole — `{lang, darken, theme, firstVisit, preVisitTime, lite}` under `localStorage["setting"]` — with `n("darken", e.theme !== "light")` as the one line relating them: the toggle writes `theme`, everything reads `darken`. Reproduced in `context/settings.js` over the same `createPersistedStore` the account uses, storing only `theme` (the other four fields have nothing consuming them here). Note the test is `!== "light"` and not `=== "dark"`, which is the original's: an unrecognised value reads as dark.

**The class is applied before the first paint**, from `main.jsx` next to `watchRemScale()`, not from a provider effect — `index.html` ships `<body class="app-root dark">`, so a saved light preference would otherwise flash the full dark palette for a frame. `applyTheme` is `QS()` ported: the class plus `meta[name=theme-color]`, and `Zi()` is `document.querySelector(".app-root") || document.body`, which here is `<body>`. **That one class does three jobs** — the palette, the `dark:` variant, and the pre-boot loader's own rules in `index.html`, which swap `init-dark.png` for `init-light.png`.

**All three sprite families are themed.** `menuicon` and `gameicon` are twelve files off `hash.game` — `_w` / `_w_h` / `_g_w` plus retinas — under the hashes `Enter-uT7xMZD7.css` already names. `coloricon` needed no new file: it is ONE sheet whose light and dark variants are separate CELLS, and all 33 families are transcribed whole into `index.css` with their `_w` / `_g_w` / `_p_w` twins.

**WHICH SHEET IS THE LIGHT ONE IS NOT DERIVABLE FROM THE FILENAME, and guessing it is what made the sidebar icons invisible in the light theme.** `NavItem-NXfL5xSI.css` says `.menu_icon_img.menu_icon_img_light { background-image: var(--menuicon-w-h-img); color: #000 }` — the light RESTING state is the `w_h` sheet, and `--menuicon-w-img` is referenced by nothing in any of the six mirror stylesheets. Measured to confirm: mean luminance over the opaque pixels is 190 for `menuicon` (`#b3bec1` exactly), 255 for `menuicon_h`, **24 for `menuicon_w_h`**, and 105 for `menuicon_w` — a mid grey that barely reads on white. The game sprite is arranged the other way round (`--gameicon-w-img` really is its light resting sheet, `w_h` its hover), so the two must not be unified.

**The original picks the sprite class in JS and this build picks it in CSS.** `ge` in `Enter-MsmOuq5R.js` is `n.select ? (darken ? i.select : i.select_light) : icontype==="tabbar" ? (darken ? i.pure : i.pure_w) : (darken ? i.normal : i.light)`. There is no shared sprite component here — eight call sites write `menu`, `chat_p`, `sports_p` and a couple of dynamic names inline — so each light cell is written as a selector PAIR (`.app-root:not(.dark) .color_icon_img.menu, .color_icon_img.menu_w`), which themes every existing call site with no markup edit and keeps the `_w` class addressable. Both halves share one coordinate, so there is nothing to keep in sync.

**Three PNGs are ink, not artwork, and vanish on white.** The wordmark `logo.png` is luminance 222; the original stores every image as a `[dark, light]` tuple behind `new Proxy(Rc, _h(t => Ce.darken ? t[0] : t[1] || t[0]))`, and `logo.base` is `[logo-CBzjipjR.png, logo_w-Vb58juxx.png]`. `logo_w.png` is fetched and picked in JS at all three consumers — the header, the region-block dialog, and `data/providers.js`, where the house studio's mark IS the site wordmark (`providerLogo` gained a `darken` argument defaulting to true, and BC.GAME is the only row with a `logoLight`). Note `logo.small` is the SAME file on both sides of its tuple, so the square mark needs no twin.

**Colours that had no token got one.** `--sidebar-row-raised` in `Sidebar.css` is the raised fill a nav row takes when hovered, expanded or current — `#3C4142`, which appears in none of the six mirror stylesheets and is this build's own measurement. **Its light value is derived rather than measured** (light layer5, the theme's own "raised control over white") and is the only such value in that file. `--footer-bg` is the opposite case: it looked like layer1 and is not, because the two coincide only in the dark theme — the light footer is pure white where light layer1 is `#EEF1F4`.

**Four close buttons invert the usual arrangement**, and it reads as a transcription slip until you check: `.pop-close`, `.dialog-close`, `.dialog-back` and `.dialog-action` are `background-color: var(--white_alpha5)` with `.dark … { background-color: #373e3f }` over it — the **token** carries the light arm and a flat **literal** the dark one. Faithful either way: in the dark theme `--white_alpha5` is a 5% white wash that would take its colour from whatever is behind the button, and the literal is what pins it.

**`text-white` ON A SECTION HEADING IS THE ORIGINAL'S OWN LIGHT-THEME BUG AND IS KEPT.** Verified rather than assumed — `useVaultPageRefresh-BbAisGjV.js` writes the Vault Pro FAQ heading `text-white mb-0 text-left text-lg font-extrabold`, its only `text-white` in 20 KB, inside a `bg-card` that is `#FFFFFF` in the light theme. So on bc.game itself that heading is white on white. `text-primary` is plainly what was meant and is one word away; it is not written, for the reason `f-ull`, `texxt-sm` and the missing `dice` sprite are kept. The weekly raffle's two headings take the same call by extension, its chunk being one of the missing ones.

**Known gaps, none of them silent:** the VIP page's `banner_bg_w` / `banner_bg_m_w` backdrops and its `-bg-light` card gradients; the deposit dialog's `lightIcon` channel logos and the Cwallet mark's light twin; the account page's `user-vip-N-*-light` gradients; and the help documents' code blocks, which stay dark in both themes **on the original too** — its `prefers-color-scheme` block only restates the colours it already sets.

## Icon sprites

Icons are not individual files. Two sprite sheets are positioned with `background-position`, both defined in `Sidebar.css` (and partly duplicated in `index.css`):

| class | sheet | `background-size` | grid |
|---|---|---|---|
| `.color_icon_img` | `assets/coloricon.png` | `301px 256px` | 32px cells, colored |
| `.menu_icon_img` | `assets/menuicon.png` | `352px 352px` | 32px cells, greyscale — sidebar rows |
| `.game_icon_img` | `assets/gameicon.png` | `352px 320px` | 32px cells — the BC Originals flyout |

**All the positions are now transcribed, so adding an icon is no longer a CSS edit.** `menu_icon_img` carried 46 hand-added rules of the source's 113 and `game_icon_img` had none of its 107; both files are in the mirror in full (`NavItem-NXfL5xSI.css`, `OriginalsGames-zlYWkqQI.css`) and both were copied whole after checking that every existing rule matched. Regenerate rather than hand-edit. `color_icon_img`'s positions are still added one at a time.

**Both sidebar sprites now have every STATE as a real sheet**, which is what the note under Sidebar used to say was impossible. The mirror saved only `menuicon_retina` and `gameicon_retina`; the rest — normal, hover, active-green and their retinas, ten files — are on `hash.game/assets/` under the hashes the stylesheets already name. The hover state is no longer a `filter: brightness()` on the normal sheet.

Note the ACTIVE state is a class ON the icon (`menu_icon_img_active` replacing `menu_icon_img_normal`), not a descendant selector off the row, so the markup swaps the class. **The `_w` sheets are local too** — six more files, normal/hover/active-green plus retinas, for each of `menuicon` and `gameicon`. Each light arm is written `.app-root:not(.dark) …`, one specificity step above the dark rule it overrides, so the dark rules are untouched bare selectors and neither needs `!important`.

One arrangement detail that bit while doing this: `menuicon.png` used to be the **retina** file under the plain name — 704×704 squeezed to 352 by `background-size`, which renders fine on its own. With three states in play the base and the `@media (min-resolution: 192dpi)` block have to be genuinely different files or the media query is decoration, so `menuicon.png` is the true 352 sheet now and `menuicon_retina.png` its twin. `coloricon.png` is still the retina file under the plain name and has no media block at all; that one is untouched.


## The dialog open animation — `N()` and `BS` are two passes, and this shell ran one

The manager runs **two independent animations** and picks each by the transition, not by the
dialog:

- **`N()` — scrim and card.** Only when the route TYPE changes BASE ↔ DIALOG (`if (W === H) return`).
  The scrim is `Qu = [{backgroundColor:"#0000"}, {backgroundColor:"#000a"}]`; the card is
  `IS = [{transform:"scale(.92)", opacity:0}, {transform:"scale(1)", opacity:1}]`. Both run with
  `wo = {duration: 300, easing: cubic-bezier(.36,.66,.04,1)}`.
- **`BS` — the slide**, on the overlayer:
  `x === "POP" && E ? c(S,2,1) : (!ee.mobile && !E ? <no slide> : c(S,0,1))`, where `E` is "the
  route we came from was already a dialog".

**`RouteDialog` was running only half of it, and the visible result was a modal that slid in where
the original's grows.** Two separate mistakes, both now fixed:

1. **Only the auth dialog applied `dialog-scrim-in` / `dialog-card-in`.** Every other dialog route
   — user-action, the verification pair, the profile family — got no scrim fade and no card scale,
   leaving the slide as the whole animation. The keyframes had been in `DialogShell.css` correctly
   the entire time; nothing outside `modals/Auth` referenced them.
2. **`open` and `push` shared the slide branch.** `!ee.mobile && !E` says a DESKTOP OPENING ITS
   FIRST DIALOG is the one transition with no slide, and `enter === 'open'` is exactly `E === false`.
   Everything on a phone still slides, because `ee.mobile` short-circuits that test on the original
   too.

A third followed from reading `BS` rather than a depth comparison: **a REPLACE between two dialogs
slides.** The country picker hands off to the verification form with `{replace: true}`, and `enter`
was derived from depth — a replace leaves depth where it was, so it came out `none` and animated
nothing. Depth is still right for the stack; it is the wrong thing to read the animation off, since
`BS` tests where you came from. `enter` now returns `push` for any dialog → dialog that is not a POP.

Verified in the browser by watching which classes land: opening from a page gives
`dialog-root … dialog-scrim-in` plus `dialog-list … dialog-card-in` and **no** slide; picker →
form gives `dialog-overlayer dialog-slide-in` and neither of the other two.

# Quest Hub, Bonus and Free Plays

Part of the bc.game rebuild notes. Index and cross-cutting rules: [../CLAUDE.md](../CLAUDE.md).

## Quest Hub

`/quests` — the original's own path, and one of the two sidebar rows that only appear once you are signed in (Bonus, `/bonus`, is the other and is not built). Its route carries `guards: [() => !b.login && "/"]` and `dialog: !!m.mobile`: the guard **is** reproduced, so a logged-out visitor is sent to `/` rather than to the sign-in dialog, while the device test is not — only the desktop page arm is built, as on `/wallet/withdraw`. `/quests/sendemail`, `/quests/bind2fa` and `/quests/bindemail` are dialog siblings there and are not built.

Sixth page built the `hash.game` way. `index-TGm-4VyO.js` is not in the mirror and came off `hash.game/assets/`, along with `section-group-l1HCczCi.js`, `badge`, `tier-icon`, `bonus-pop`, `claimable-item-detail`, four icon chunks and the page's own stylesheet — so every class list, every string and every group heading below is the deploy's own and **nothing on this page is read off a screenshot**. `quest-service-Cob0DDxX.js` was already in the mirror.

**Its stylesheet is a decoy worth knowing about.** `index-D_qd3jqG.css` is named in the chunk's `__vite__mapDeps` and holds nothing this page uses — flip-card keyframes, gold text gradients, a `shadow-button` with a 16° X-rotation. All of it belongs to `/challenge`, the scratch-card sibling that shares the chunk. The quest page is pure utilities.

**THE CHUNK IS REAL AND THE PAYLOAD IS NOT, and that split is the thing to hold on to.** All three feeds are login-gated and `hash.game` answers **403** — not the 6002 the deposit paths give — which was checked rather than assumed. So `pages/Quests/quests.js` is the service's own `initialValue` shape filled with what the capture renders. Exactly one field in it is inferred and it is flagged there: `second: 'wallet'`, the group tag. Six tags map to GETTING STARTED and `wallet` is the only one that names a wallet-connection quest, but the tag itself is server-side and was never seen.

**One quest handler of ten is built, and that is the whole of what the capture shows.** `Ke` is a ten-entry registry and its ARRAY ORDER is what decides the order the group headings come out in — the store walks it, buckets each quest under `Ea(entry.second)`, and the map's insertion order is the render order. All ten names are kept in `QUEST_HANDLERS` for that reason: deleting an unbuilt one would silently reorder the page the day it lands. `newcomerQuest` is in the response type but *not* in the registry — it drives the Lucky Rookie Quest banner above the tabs, which is gated on its own `isVisible()` and is absent from the capture.

The built one is `cWalletConnectionBonus`, and reading its card off the chunk explains every pixel of it: `rewardAmount` is `boundAmount ? printCurrency(…) : undefined`, the lock glyph beside it renders only *inside* that same `Show`, and the right-hand column is `justify-between` when there is a figure and `justify-center` when there is not — which is why the capture's Connect button sits vertically centred with nothing above it. The button says "Connect" rather than "Claim" because `rewards` is empty. Its action emits `open-cwalletbind`; that dialog is not built, so the button is inert, as is the ƒ(x) chip's popup (`Wi` — a three-step "How You Earn" list over six rules, all verbatim i18n in the chunk).

Four things the chunk settles that a screenshot rebuild would have got wrong:

- **`"unLockRate" in e` is an `in` test, not a truthiness test**, and the footer's "One-step task" line depends on the difference: a quest that OMITS the field gets no line, one that passes `null` gets one. The Cwallet quest passes `null`. Reproduced with `Object.hasOwn`.
- **The In Progress tab's empty state is a spinner, not a message.** The fallback branches on `we.bcmx` and only that white label gets "No quests in progress"; bc.game takes the other arm, a `min-h-40` box holding the site's own `.loading`. So an empty in-progress list spins forever. Unreachable with this fixture, which always carries the Cwallet quest.
- **The Completed tab splits at thirty days on `createTime`, not `completedTime`**, and folds the older half behind a toggle that starts closed.
- **`Ee.mobile` decides the completed/expired list's STRUCTURE**, not just its width: a desktop gets a two-column grid of individually bordered cards, a phone gets one bordered box with hairlines between rows. A device test, so only the desktop arm is built; both lists are empty anyway.

**Two tokens were added to `@theme` and one of them needed SCOPING, which is the finding to carry forward.** `--main` (#e4eaf0cc, `--fourth`'s #E4EAF0 at 80%) is what `[&_.tabs-indicator]:bg-main` makes this page's underline — near-white rather than `.tabs-indicator`'s brand green. `--card` is the other, and `.app-root.dark .bonus-scope` re-declares it: 30 33 33 globally, **23 26 26 inside the scope**. Diffing that block against the global dark one rule-for-rule turns up exactly two values that differ, and the second is the one that matters — **`--quarterary` is #A1AFB2 globally and #697072 inside `bonus-scope`, a step and a half darker**. This page spends it on every group heading, every card description and the "One-step task" line, so getting it wrong would wash the whole page out. Both now sit in a plain `.bonus-scope` rule in `index.css`; declaring custom properties on a class and letting `bg-card` / `text-quarterary` resolve them at the use site is the ORIGINAL'S own mechanism, not a workaround. The promotions page — the only other `bonus-scope` consumer — uses neither token, which is why this never surfaced before.

**The empty state finally has its crocodile.** `ks` in the main bundle draws `<img class="w-48 h-48">` over its message unconditionally; the image map is assembled at bootstrap (`const oh = {}`, filled by `eb`), so the mirror's copy read as empty and `components/Explore/GameGrid`'s `Empty` was built without it. The file it names, `/assets/empty-6mO-ndW8.png`, came off `hash.game`. The component moved to **`components/shared/EmptyPlaceholder`** under the second-call-site rule and `Empty` is now a re-export — so the Explore and casino grids gained the artwork too. Note `ks` sets NO colour on its message div: the colour comes from whatever wraps the section, which is why the quest tabs wrap it in `text-quarterary` and the grid passes `text-secondary` down.

**`components/shared/Loading` moved for the same reason** — only the spinner, not the whole of `AfterLogin/icons.jsx`: `sa` belongs to the main bundle and any page can want it, while the rest of that file is the account dropdown's own drawings. `IconLoading` there is a re-export, so the currency dropdown's call site is unchanged.

The tab indicator is **measured**, as the promotions page's is and for the same reason (`max-w-fit` tabs with a `gap-6`). It uses `clientWidth` and `offsetLeft` — the component's own two properties, since `offsetLeft` already resolves against the `position: relative` `.tabs-title` — where the promotions page subtracts two bounding rects because its group can carry padding. `SectionGroup` (`_` in the section-group chunk) is kept in `pages/Quests/` rather than lifted; move it the day a second bonus page renders one.

Two more things not built, each a real component: the Lucky Rookie Quest banner, and the `px-4 sm:px-0` gutter on the page root, which is **this build's** — below 640 the original serves a dialog, so its page arm (heading `hidden … sm:block`, card with no fill and no padding) never renders there.


## Bonus

`/bonus` — the Quest Hub's sibling, and the other sidebar row that only appears signed in. Its route carries the same pair: `guards: [() => b.login ? !1 : "/"]`, reproduced inside the page, and `dialog: m.mobile ? {behavior: "no-title"} : !1` — and unlike the Quest Hub beside it, **both halves are honoured now**. `ke` is the side-by-side pair of cards the desktop capture shows; `Te` is a two-tab strip (Rewards / VIP) over the same two panels on a phone, and `Rewards`/`Vip` are handed to whichever layout untouched, exactly as the chunk hands them over as `e.rewards` / `e.vip`.

**THE MOBILE ARM IS A DIALOG WITH NO TITLE BAR, AND THE BACK ARROW IS THE TAB STRIP'S.** `behavior: "no-title"` is not a style on the bar, it is the bar's absence: the manager writes `I(x, !y && C(FS, …))`, so nothing renders it, and `Y("dialog-item", (v || y) && "dialog-transparent-title", y && "dialog-no-title", …)` marks the item so the content keeps its own gutters. What replaces it is `Te`'s `tabTitlePrefix` — `iT` renders that prop as the first child of `.tabs-title`, ahead of `.tabs-btn-group` — holding a `size-10 -ml-2` button that calls `navigate(-1)`. So the strip is the chrome. `components/shared/RouteDialog` gained a `noTitle` prop for it and `pages/Bonus/Dialog.jsx` is the three-line mount, the same shape `/wallet/withdraw` and `/referral` already had.

Three details of `Te` that are easy to lose. **The `TabItem`s carry a title and a class and NO children** — the panels are rendered as the layout's own siblings under two `<Show>`s — so the Tabs still draws its content box for the selected tab and that empty box's `.tabs-content` `margin-top: .5rem` **is** the gap between strip and panel; drop it as "an empty div" and the gap closes. `class` on a `TabItem` belongs to the CONTENT PANEL, the fifth page here to need saying, which is where `!bg-layer1` lands. And `.bonus-v5-dialog` is a REAL class in `index-DxOqNczA.css`, not a marker: it paints `.dialog-content` layer1 (the page's own `bg-layer1` only reaches as far as its content) and zeroes the scroll container's bottom padding. This build writes that second rule as `.bonus-v5-dialog .dialog-content > .scroll-container` — a specificity bump, not a value change, because the shell's competing rule is 0,2,0 in a different file and source order should not decide it.

`z-80` on the strip is live rather than the `w-30` trap: `.z-80 { z-index: 80 }` really is in the original's stylesheet.

`bonus-v5-page-dF3gugl8.js` for the page and **`index-CUb2-xA-.js`, 166 KB**, for the reward registry, plus `row-group`, `redeem`, `use-claim-all`, `claimable-item-detail`, `welcome-shield`, `error-fallback`, `empty-placeholder`, `badge` and four icon chunks — all off `hash.game/assets/`, none in the mirror.

**THE FIXTURE IS NEITHER CAPTURED NOR INVENTED: IT IS THE SERVICE'S OWN DEFAULT, and that is the finding to carry forward.** `rewards-service-CxFWsPYn.js` **is** in the mirror, and it wraps `POST /activity/bonus/v2/` in a resource whose `initialValue` is declared inline — the payload a logged-out visitor renders. It holds six reward types (`instant_bc`, `rakeback`, `month_bonus`, `weekly_bonus`, `level_up_bonus`, `daily_bet_back_bonus`), each one empty entry from the same factory, with `unclaimedCount: 0`. That is *exactly* the six rows the capture shows, in the two sections it shows, behind the same greyed-out Claim All — the captured account is fresh enough that the real response and the logged-out default render identically. So a login-gated endpoint cost this page nothing. **Before writing a fixture for anything behind a login, check whether the service module declares an `initialValue`**; it is a third route to ground truth beside a captured response and a `system/conf` path that answers.

**AND THAT DEFAULT IS NOW THE SHAPE A LIVE READ IS FILLED INTO, rather than the whole payload.** Against the iBitPlay backend four of the six rows are real — `daily_bet_back_bonus`, `weekly_bonus` and `month_bonus` off `GET /user/bonus`'s `types`, and `rakeback` off `GET /user/rakeback`, which is its own module with its own currency. `instant_bc` and `level_up_bonus` have no equivalent and keep the declared default, which is the same thing they already rendered. **`extra.nextClaimTime` is what the mapping turns on**: `RewardStatus`'s arm order means a recurring type carrying it prints "In Progress" and the amount arm never runs, so it is KEPT while `claimable` is false and DROPPED when it is true. `eligible` is deliberately not consulted — it answers whether your VIP level reaches `minVipLevel`, not whether there is anything to take, and the original renders an ineligible row exactly as it renders an empty one. A zero amount produces no ITEM at all, which matters past this page: the account dropdown's gift counts `canClaim ? items.length : 0`. The row's hardcoded `amount={0}` — correct while the zero arm was the only reachable one — now sums the entry's items, which is the chunk's own last arm and is byte-identical on an empty list.

**One field is derived rather than recovered**, and it is flagged at the data: `extra.nextClaimTime` on the three recurring rows. The default factory carries `extra: { end: true }` and no timestamp, which would send those rows down the amount arm instead of the "In Progress" arm the capture shows — so the live response plainly carried one. Its value is not recoverable, because "In Progress" wins the switch before the countdown arm ever runs and nothing prints it. Rather than pin an invented instant it is computed from each bonus's own stated rule, which is written on the cards themselves ("Drops the next day UTC", "every Friday UTC", "every 15th UTC") — the same treatment `/deposit-offer`'s month reset and the weekly raffle's draw clock get.

**A row's right-hand column is a SWITCH and its arm ORDER is the whole of its behaviour**: settling, then "In Progress" for a *recurring* type that has a next-claim time, then a countdown for anything else that has one, then a zero figure when the entry has no items, then the grouped amounts. That ordering is why Daily / Weekly / Monthly read "In Progress" with no clock beside them *even though a clock is configured for all three* — the recurring arm matches first. The countdown is built anyway, because Reload and Welcome Bonus are not recurring and do print theirs.

Four more things the chunks settle:

- **`--card`, `--quarterary` and `--secondary-light` all differ inside `bonus-scope`**, and this page is the first to need all three. The scoped block was added with the quest page (see there); `--secondary-light` is the new one and is declared ONLY inside that scope on the original — 149 122 255 in the dark arm — so it goes straight into `@theme` with no override, since there is no outside value to fall back to. It is the "M" of Monthly Bonus and the monthly countdown's tint.
- **The page repaints the app background** — `Me` ships an inline `<style>` setting `.app-root { background-color: rgb(var(--layer1)) !important }`, so `/bonus` is a step darker than every other route and the two panels' layer2 fill reads as raised. Reproduced with the same mechanism, a style tag inside the page, so it unmounts with the page and nothing has to undo it.
- **The D / W / M beside the three recurring rows are not icons.** `fn`/`wo`/`$o` are `<span class="text-base font-extrabold text-brand|text-warning_brighter|text-secondary-light">` holding one letter each. Easy to spend an hour hunting for as SVGs.
- **`row-group` and `card-group` are real rules and the page uses one of each.** A row group is one bordered box: every child takes a full border and square corners, each after the first is pulled up `-1px` so adjacent borders overlap into a single hairline, and only the outer corners round — with `:only-child` rounding all four so a one-row group is a plain card. A card group is the same border on every child with a 12px radius all round. Both went into `@layer components`, and for `display` that is not optional: an unlayered `display: grid` would outrank any responsive visibility utility on the same element, which is the trap `.center` sprang on the tabbar.

**`src/data/vipConfig.js` is new and it is a CAPTURED response** — `/api/game/support/vip-v2/config/` was already in `endpoints.js` under the captured group and in the mirror under `bc.game/bc.game/api/`, and nothing had read it until the level card needed a tier name and a next-level target. Thirty-four levels across eight tier families. **Ten of the thirty-four names carry a raw newline where a space belongs** ("Bronze\nIII"), which is the live payload's own and is reproduced: the site derives a level's tier family by splitting on the LAST SPACE, so a name with no space yields the whole string as the family, nothing matches in the icon or colour maps, and those ten levels draw the Beginner glyph in `currentColor`. The newline never shows — HTML collapses it — so the icon is the only tell.

**That ladder corrected the account fixture.** `SIGNED_IN`'s XP was invented before the config was in the project: 1000/1200/2000 matches no row in it, and the level card looks its next tier up by `minXp === levelEndXP`, so it found nothing and printed the original's own `--`. It is level 3's real band now, 7000..15000 with `currXP` a fifth in, which keeps the 20% the header ring was invented for and prints "6.4K XP to Bronze IV". Note the capture is a **level 0** account (Beginner, 0.00%, "1K XP to Bronze I"); this build renders level 3 because that is what its fixture says, not because anything differs.

The **VIP panel has three states off one field** — `hostCard.userProfile`: 0 is everyone, 1 is "YOU ARE IN!" with a two-row VIP perks list and a Talk to Host button, 2 is the Your VIP Host card with an avatar and a Telegram handle. **Only 0 is built**, which is the capture, because there is no `hostCard` in any captured response and no endpoint here answers for one — the other two arms would be inventing an account relationship. The branch is left in place with its arms named.

Two shared components moved under the second-call-site rule: **`components/shared/SectionGroup`** (`_` and `w` in `section-group-l1HCczCi.js`, out of `pages/Quests/QuestCard.jsx` — the chunk exports the heading and the plain `Card` together and this page uses both) and **`components/shared/Loading`**, which had moved for the quest page one build earlier.

**The icons are GENERATED, not transcribed** — twenty-one of them, from six chunks, by a script that closes Solid's unclosed tags, camel-cases the attributes and strips full-viewBox clip paths. Two traps it had to learn, both already documented for BetBy and both real here: `<path>` and friends are effectively VOID in these templates, so treating them as containers leaves a stray `</path>` behind whenever a subtree is dropped; and the two genuine clips that survive were renamed off their one-letter ids, since inlining a duplicate `id="b"` breaks every later reference.

Not built, each inert at its call site: the ƒ(x) popup behind every chip (a different component per reward type), the claim flow behind Claim All and behind a row (`/activity/bonus/v2/batch-claim/`, authenticated), the redeem submit, the Welcome Shield banner between the header and the sections, and the whole VIP Rewards section — its six reward types are all absent from the payload, and a section with no rows does not render.


## Free Plays

`/free-plays` — what the account dropdown's Free Plays row opens, and the **third dialog route** in this build after `/login/*` and `/deposit`. `free-play-DOTFWZ2M.js` is 6 KB and holds the whole thing; it is not in the mirror and came off `hash.game/assets/`, with `claimable-item-detail-DA9ukfTK.js` for the row's detail popup and `index-C4dmninU.js` (which **is** in the mirror) for the two sports-provider marks. So every class list is the Solid template's own, every string is verbatim i18n, and nothing here is read off the screenshot.

**No guard, and that is the route rather than an omission.** `{path: "/free-plays", component: c(() => L.FreePlay()), info: {dialog: !0}}` sits in `Fg`, which `routes()` spreads flat with no group guards — unlike `/deposit`, whose own guard bounces a logged-out visitor to `/login/regist`. Nothing is needed either way: the row that opens it carries `needLogin`, and the fetcher is `if (login) return post(…)`, so a logged-out visit renders the identical empty dialog.

**`dialog: !0` with no `size` means the manager's own default, and that is what finally hoisted the card treatment.** `.pc .dialog-list` on the original carries 30rem × 40rem, a 1rem radius and the layer2 fill, and a dialog that asks for its own size gets it written inline over the top. The two dialogs here had each restated the radius and the fill beside their own size, with a note saying to hoist the pair the day a third one needed it — this is that third one, and it wants the default outright. `Auth.css` now carries a real `.dialog-list` rule inside its `@media (min-width: 1024px)` block and the two `.dialog-list.<name>` size classes override nothing but width and height, which is the original's arrangement. `.dialog-list.<name>` is 0,2,0 against 0,1,0, so source order between the two files cannot matter. The 30 × 40 checks out against the capture at dpr 1.25 (595 × 800 image pixels).

**THE FREE SPIN HALF IS LIVE AS OF 2026-09-04, and the paragraph below describes what the FIXTURE arm still does.** `GET /casino/gis/freespins/mine` was built for this dialog (Part 4b.18 of `docs/backend-gaps.md`) and is the only player-facing read `gis_freespins` has ever had — its three existing routes are all staff ones, which is why this tab was empty rather than broken. **The Free Bet half stays empty and cannot be filled**: a free bet is a sports bonus carrying `provider: "bti" | "betby"`, neither is configured, and this platform has no sports free-bet table for one to be granted into. So "No Free Bets Yet" is now a true statement about the platform rather than a placeholder. Two adapter decisions are argued in `services/freePlay.js`: `bonusSource` has no equivalent here (a campaign carries an operator-chosen id, and a raw id in a title reads as a bug), and `iconThreeFour` is resolved from `src/assets/games` with `assetExact` because there is no artwork anywhere in the database — `assetFor` would have put another game's cover on a free spin.

**THE PAYLOAD IS ABSENT AND THAT IS THE CORRECT RENDERING — the fourth wallet-family page in a row where being locked out is the right answer.** `POST /activity/bonus/freeplays/unused-rewards/` answers **403 with an empty body** (probed; not the 6002 the payment paths give, and not the transaction pane's Spring page either), and the resource declares **no `initialValue`** — so `data` is `undefined`, which is a state every read in the chunk guards for with `?.`. All 0 / Free Spins 0 / Free Bet 0 over "No Free Plays Yet" is the capture, reached without inventing anything. Note the contrast with `/bonus`, where checking for an `initialValue` is what supplied the fixture: here there is none to find, and the absence is itself the answer.

The endpoint is **not** in a service module like the rest of the bonus family — `ws` is declared in `Enter-MsmOuq5R.js` itself. `Wo` wraps it so **one resource is shared by both consumers**, this dialog and `FreePlayDot` on the dropdown row, which is why the badge and the tab counts can never disagree. That chunk is recovered too (1.1 KB): a `<Badge value={0} type="dot"/>` behind `!license.bcmx && totalCount > 0`, so at count 0 the correct rendering is nothing — the dropdown's empty dot slot was already right, for a reason that is now known rather than assumed.

Four things the chunk settles:

- **The root is `PageLayout` (`w3`) and it draws nothing.** Three lines: inside a dialog route it pushes its own props, minus children, into the router's dialog context and returns `t.children`. So `title` becomes the manager's title bar and **`class` lands on `.dialog-item`** — which is why `bonus-scope bg-layer1` reaches the whole panel and why `[&_.dialog-title]:bg-transparent` is a descendant selector that resolves at all. The same helper is why the deposit and withdraw panes have no heading.
- **That transparent-title class is inert here.** On the original `.dialog-title` fades from transparent to layer4 as content scrolls under it (`--tw-bg-opacity: calc((var(--scroll) * 100 / 15) - 50%)`), and this dialog opts out. In this build that fill is transcribed **scoped** — `.user-enter-dialog .dialog-title` in `UserEnter.css`, the one route that needed it — and the shared rule paints nothing, so the bar is already transparent. Kept like `f-ull`. Before hoisting that fill onto the shared rule, note the class would not then cancel it: an unlayered `.dialog-title` beats a Tailwind arbitrary variant regardless of specificity, so the opt-out would have to move into CSS beside it.
- **The three blocks are siblings in the scroll container and `flex-1` on the middle one is what pins the footer.** `.scroll-container` is `flex flex-col` with `min-height: 100%`, the list grows into whatever is left, and the button's `sticky bottom-0` holds it there once the list is long enough to scroll. Its `bg-layer1` is not decoration — it stops rows showing through the strip, and it has to match the panel's fill.
- **The tab order is not the branch order.** The strip reads All / Free Spins / Free Bet, and the panel memo tests index 0, then **2**, then 1. Each tab also carries its own empty message ("No Free Plays Yet" / "No Free Spins Yet" / "No Free Bets Yet"), so the crocodile's caption changes with the tab.

**The row is built even though the feed can never reach it**, because the chunk gives it in full and both provider marks were recoverable — `bti-DMR0aXP3.png` off `hash.game/assets/` and BetBy's decoded out of a base64 data URI in `index-C4dmninU.js`. Three things about it:

- **One object read two ways.** The minified source declares `r = () => n.item` and `o = () => n.item` — two aliases for the same value, a TypeScript cast surviving minification — with `bonusType === "Free Spin"` picking. There is no second shape to hunt for; the fields simply differ per branch. A free spin shows its own 3:4 game art, its game name in `mail` and `20 x <coin> 0.2 BCD`; a free bet shows a 36px provider mark in a tinted 60px square (brand green at 5% for BTi, a literal `rgba(133,103,255,0.05)` for BetBy) and no second line.
- **Play Now's free-spin arm has a bug that is reproduced rather than tidied.** `C() && m("/trading")` has no early return, so a `detrade:trading` free spin navigates to `/trading` and then straight on to `/game/…` in the same handler; the second call wins. Neither destination is a route here, so the button is effectively inert — but the currency write on the free-bet arm is real, and it is this project's `setSetting`, the same setter the wallet pill uses.
- **`--mail` is a new token and it exists only inside `bonus-scope`** on the original, light arm and dark arm both, exactly as `--secondary-light` does. So the dark value (`#D5E2E5`) goes straight into `@theme` with no override, since there is nothing outside the scope to fall back to. Its value is `primary_alw`'s exactly, but the two are separate names that diverge in the light theme, so they stay separate for the reason `card_dark` and `alw_dark` do.

**"Get More Free Plays" goes to `/promotions/promotion`** — the chunk's own `u("/promotions/promotion")`, and that page is built, so the button is the one control here that fully works. No `type` on the Button, so it takes nothing from the type map at all: a bare `.button` with `border border-third` written at the call site, which is what makes it read as an outline rather than a fill.

Not built, each inert at its call site: the **claimable-item detail popup** behind a row's title (`at(list.map(rt), index, !0)` — a `.pop` over a CAROUSEL of the whole list rather than the one row, which is why it takes a list and an index; `rt` is ported as `toClaimableItem` because the mapping belongs to this dialog even though the popup is a shared bonus component), the `ErrorBoundary` around the list (only a real fetch can fail). Its `Suspense` sibling IS reachable, and its `fallback: null` is deliberately NOT ported literally — the three tab counts above the list read the same payload, so drawing nothing would leave 0/0/0 over a blank panel; the site's spinner in the panel says what the boundary means, and the 10s cache on the resource, which is one line at the seam whenever fixtures come off.



## The Redeem input — the last of `/bonus`'s six routes

`jt` in `redeem-M5TwYr_j.js` (fetched from `hash.game/assets/`, not in the mirror). The markup was
already this build's; what was missing was the submit, which the note there described as "not
built, so it stays disabled until you type and does nothing when you do."

**The original does not call the API from that component.** `Et(Tt)` pushes a POPUP:

```js
const Tt = code => { W || popup.push(() => <Show when={login} fallback={<SignIn code/>}>
                                              <RedeemResult code/></Show>) }
```

`W` is a one-at-a-time guard, and `_t` is the result screen: a **"REDEEMED!"** heading over one row
per reward, each naming its type and where it landed — "Added to Lottery", "Added to Lucky Spin",
each a link into that feature.

**The platform answers one amount, not a list.** `{code, amount, currency, newBalance}` in the
bonus currency, with no reward types and nothing for those rows to be built from. So the result is
a toast carrying the site's own "REDEEMED!" and the figure; the dialog is worth building the day
the platform returns a list, and not before, because its whole structure is that repeated row.

### A redeem code belongs to an account

The lookup is `where: {userid: userId, code}` — these are codes **issued to a player**, not
campaign codes a stranger can type. Another account's code answers `404` exactly as a made-up one
does, and there is no player-side route that mints one. `GET /user/bonus/codes` is the visitor's
own list, paginated and empty on this delivery.

The code is sent **raw**: the server trims and upper-cases before the lookup, deliberately — "so a
player typing a code from a screenshot in lower case still matches" — which is checked rather than
assumed (`testcode-1` redeems `TESTCODE-1`).

Both refusals carry the platform's own words and are shown as they come:
`404 CODE_NOT_FOUND` → "That redeem code is not valid", and `409 CODE_NOT_ACTIVE` → "That redeem
code has already been used or has expired", which is also the arm for a zero-value code and for
losing the update race, since the UPDATE is guarded on `status = active`.

The amount arrives as a decimal string at the wallet's eight places (`"25.00000000"`); trailing
zeros are trimmed for the toast and nothing is rounded, because a bonus figure that changed on the
way to the eye would be worse than a long one.

Verified against the running platform on seeded codes, all three arms: an unknown code, a
`redeemed` one, and an active one typed in lower case — which credited 25 BJB and cleared the
field. The two codes, the credit and its ledger rows were removed afterwards.

## My Profile

`/user/profile/:userId` — what the account dropdown's My Profile row opens, and **the first feature here that is three dialogs rather than one**: its two Details links push `/user/medals/:userId` (Master Medals) and `/user/statistics` (Statistics details) on top of it, each drawing the manager's back arrow instead of a second close square. All of `src/components/modals/Profile/`.

**IT IS IN THE `account` FEDERATED REMOTE, WHICH IS THE HELP CENTER'S FINDING PAYING OFF A SECOND TIME.** `Enter-MsmOuq5R.js` resolves all four profile routes through `w = zt(vo)` with `vo.moduleName = "account"`, so none of them is in `/assets/` at all — and the mirror saved that remote **without** its lazy chunks, exactly as it saved `static` and `games` without theirs. `hash.game/modules/account/remoteEntry.js` → `manifest-zssWG_dx.js` (which IS in the mirror) carries the exposes map and the remote's own `__vite__mapDeps`, so the four chunks came off `hash.game/modules/account/assets/`: `index-BkEDN5Nc.js`, `index-D0DujHZT.js`, `index-DVoHgAYe.js` and `Tool-CuKFgBKm.js`. Every class list is the Solid template's own and every string is verbatim i18n. **When a component is not in `/assets/`, check whether its route resolves through a remote before assuming a screenshot rebuild.**

**FIVE ENDPOINTS, AND THREE OF THEM ANSWER — the `game/support` rule holding for a sixth family, with one exception worth understanding.** A catalogue answers, a per-account read does not, *even when both live under the same prefix and both take a `userId`*:

| path | answer | what it is |
|---|---|---|
| `achievement/all/` | **answers** | the 23-medal catalogue, holder counts, progress bands |
| `user/game/summary/` | **answers** | wins / bets / wagered for any userId |
| `achievement/<userId>/` | **answers `[]`** | another player's medals |
| `user/info/<id>/` | 6001 | the profile itself |
| `user/game/detail/` | 403 | the per-currency statistics rows |

`summary/` is the exception and it is not really one: it aggregates **public bet history**, so 105522617 comes back with 25568 bets and $24,659.79 wagered — and for this build's own fixture account id it answers `{betNum: 0, winNum: 0, betAmountUsd: "0"}`, which is the capture's three zeros arrived at without looking at the screenshot. The lesson generalises: **an AGGREGATE over public data is public; the ROWS behind it are not.** Note also that `user/info/` returns 6001 `illegal_request` rather than 403, for real ids as well as invented ones — a signature requirement, not a missing session.

**`src/data/achievements.js` is that live catalogue**, and three of its fields are necessarily zero (`medalCount`, every `status`, every `createTime`) because a logged-out request has no account to report on. That is what a fresh account has anyway, which the capture confirms. **`count` drifts daily** — the page says so itself — so the numbers sit within a few hundred of the capture's (12765 against 12778) rather than equal to them. Not a transcription error in either direction.

**The profile payload is `es`, the resource's own `initialValue` — the THIRD time checking for one has supplied a login-gated fixture** (after `/bonus`'s reward list and the referral dashboard's request-module default). Two fields are filled from the session's own account fixture rather than left at zero, and neither is invention: `userId` (0 would trip the route's own `!userId && navigate(-1)` guard) and `createTime` (0 would print "Joined on 1/1/1970"). Everything else stays as declared, which is what makes the dialog render the capture — Medals 0, three zero statistics, the crocodile under Top 3 Favorite Games, and **no Wager Contest card at all**, since that one is `<Show when={contest.length > 0}>`.

**`ss` is a sort PLUS ONE MOVE, and it is why the medal strip reads oddly.** `sort by type ascending`, then `pop()` the last row and `splice(8, 0, …)` it back — so type 21, Puzzle Unifier, lands **ninth**, between Invincible Lucky Dog and Roll King, which is exactly where the capture has it. Nothing in the chunk explains why; it reads as a hand-placed feature medal. Verified against the capture's full 23-tile order. The four type-17 rows tie on `type`, so their relative order is `Array#sort`'s stability, i.e. the feed's own.

Five more things the chunks settle, each one a thing a screenshot rebuild would have got wrong:

- **"0/20 Completed" is not a count of anything on the page.** The `/20` is a **literal** in the template and the figure before it is the unlocked count — so a page listing 23 medals says 20, which is the gold chest's own `num`, the top reward tier. Do not "fix" it to 23. One **requested departure** sits on that span: the chunk writes `mx-1`, which opens 4px on both sides and reads as "0 /20 Completed"; it is `mr-1` here so the fraction closes up against the count, which is also how the capture reads it. A one-word revert.
- **The progress bar has a 10% floor**: `((medalCount / 20) * 90 + 10).toFixed(2)`, so the brand fill is visible under the flag before anything is earned. Its pointed right end is that fill's own `rounded-md` on a 6px bar.
- **The tick markers above it draw nothing, on the live site too.** Their class is `triangle-layerbrand`, which is in **neither** the mirror's six stylesheets **nor** the current deploy's `index-DGr5jguQ.css` — both checked. Only `.triangle-layer5` exists. So each marker is a zero-size empty div, kept like `f-ull`; borrowing `.triangle-layer5` would add a grey arrow the original does not draw.
- **`btn-like` is LIVE, not a dead class**, and it is easy to file with `header-nav-item` by mistake: it is `user-select: none; touch-action: manipulation` plus every one of `.button`'s interaction rules — the `:active` brightness-and-1px-drop and the desktop-only hover brightness — with none of its box, so a `<span>` presses like a button. Already in this project's `index.css`. The odd part is that only **one** of the page's two Details links carries it; that is the chunk's own inconsistency and is reproduced.
- **`test-base` and `y-3` are typos and are load-bearing by accident**, like `texxt-sm` on the weekly raffle's table: neither class exists, so the Statistics heading inherits the body's 14px instead of being set to 16, and the stat cells take their rhythm from `h-[4.375rem]` plus `pt-1`. Both are kept as written. The stat cells also **wrap by index, not by CSS** — `w-[49%]` for indexes 0 and 1, `mt-2 w-full` after — so the third is a full-width row rather than a third column that happens to wrap.

**All 63 pieces of artwork are the deploy's own**, under their filenames minus the content hash: 50 medals (25 types × locked/achieved), eight treasure chests, the generic box, the start flag, the featured-medal glow and the favourite-game fallback cover. Five of those were base64 data URIs inlined in the chunks rather than files — types 4, 9 and 14's locked art plus the flag and the glow — and were decoded rather than fetched. `medalArt`'s key is the type, with `_BTC`/`_DOGE`/`_EOS`/`_ETH` appended for exactly those four subtypes; `cs` does the same, which is why a `subType` of `"0"` resolves to the bare type. The achieved half of every pair is unreachable while the feed reports every status locked, and is fetched anyway rather than left as a hole — the same call the Free Plays row's provider marks got. The `_w` light-theme chests and `detail_ko` are deliberately not fetched, for the reason the VIP page's light backdrops are not.

**`components/shared/DialogShell` is new and it is the DESKTOP-CARD arm of the dialog manager's shell** — a centred `.dialog-list` with a title, a close square and a conditional back arrow. `components/shared/RouteDialog` is the **phone arm** of the same `FS`, whose title bar branches on device rather than on the dialog: a phone gets the arrow and no cross, a desktop gets the cross and shows the arrow only off the stack's depth. Read the pair together; merge them the day one route needs both arms. Auth and Deposit still write their own shells, each for a reason (a `transparent-title` bar with the content pulled up under it; a per-route `size` class over a shared Panels split), and are the next to migrate. **The back arrow is the DIALOG STACK's depth on the original** (`stacks.index() !== 1`), which this build has no equivalent of — but all three dialogs are real routes, so one step of history lands in the same place. Its `pc` box (1.5rem around 0.875rem, `position: absolute; bottom: 1rem; left: 1rem`) went into `Auth.css` beside `.dialog-close`; `.route-dialog .dialog-back` is 0,2,0 against it and so still wins wherever it applies.

**THE TITLE BAR'S FILL IS `info.titleColor`, WHOSE DEFAULT IS LAYER4** — `#323738`. The manager writes it inline as `--bg` (`Rt(u, "--bg", t.titleColor)`) and `.dialog-title` reads `rgb(var(--bg) / …)` off it, so every dialog that names no colour gets layer4; the deposit route is the one that overrides it, to layer2, and the Free Plays dialog opts out of the fill altogether with a class. `DialogShell` takes it as a prop defaulting to layer4 and writes a plain `backgroundColor` inline rather than going through `--bg`, because the shared `.dialog-title` rule deliberately paints nothing: the original's fill is **scroll-driven** (transparent at rest, fading to `--bg` as content passes under an *absolute* bar) and only `/user/enter` needed that, where it is transcribed scoped as `.route-dialog .dialog-title`. This bar is a static flex sibling above the scroller, so it wants the end state and has nothing to animate — and keeping it inline is also what stops it reaching the deposit and auth dialogs, which write their own shells and have each been checked as they are.

**THE ENTER MOTION IS THE STACK'S, NOT THE DIALOG'S, and that is the part worth carrying forward.** It is not CSS on the original — three `element.animate()` calls sharing one options object, `{duration: 300, easing: cubic-bezier(.36,.66,.04,1)}`:

- the **scrim** (`.dialog-root`) fades `#0000` → `#000a`
- the **card** (`.dialog-list`) scales `.92` → `1` with opacity `0` → `1`
- an **item** (`.dialog-overlayer`) translates between `sp = { 0: "100%", 1: "0%", 2: "-17%" }`

and **which of them runs is decided by the TRANSITION, not by the dialog.** `N()` runs the scrim and the card together only when the route type changes BASE ↔ DIALOG — `if (W !== void 0 && W === H) return W` bails out when it did not — while `BS` runs the slide per item, taking its direction from the navigation action: `x === "POP" && E ? c(S, 2, 1) : c(S, 0, 1)`, with `E` being "the route we came from was already a dialog". So:

| transition | scrim | card | item |
|---|---|---|---|
| page → dialog | fades in | scales `.92` → `1` | — |
| dialog → dialog, PUSH | — | — | `100%` → `0` |
| dialog → dialog, POP | — | — | `-17%` → `0` |

**That third row is the one that bit, and the shape of the mistake generalises.** `enter` was first derived from `onBack` — the same flag the back arrow uses — which is wrong because *the dialog you pop back to has no arrow*, so it looked like a first open and re-ran the scrim fade and the 0.92 card scale. That reads exactly as the dialog closing and reopening, which is what it was reported as. A transition has a direction; a component does not. `enter` is now computed in `App` off `useNavigationType()` and the depth delta, threaded down through the dialogs, and `prev === 0` is the BASE ↔ DIALOG test — which also gets browser-Back-into-a-closed-dialog right, since re-entering the stack from a page is an open whichever way history moved. Replayed over five sequences before it was believed.

Note the outgoing `c(S, 1, 2)` — `0` → `-17%` — has no counterpart here, which is why the pop's `-17%` start looks like it comes from nowhere: on the live site that dialog really is sitting a sixth of the way off to the left, waiting. Keep it anyway; it is what makes the return read as the card settling back rather than as a fresh slide.

Reproduced in `DialogShell.css` as keyframes (a keyframe cannot be a utility, and a one-shot enter has nothing to drive imperatively — the call `AfterLogin.css` makes for `fadeUp2`). **The slide goes on `.dialog-overlayer` rather than the card**, and that placement is load-bearing: `.dialog-list` carries `overflow: hidden`, so a translate from 100% is clipped to the card's own edges instead of sweeping across the page. **Enter only** — the outgoing half needs both dialogs mounted at once, which the original's stack provides and this build's one-pathname-one-component swap does not; `fadeUp2`, the PopCenter sheet and the confirm dialog's scale all stop at the same place for the same reason.

**Two traps hit while building this, both worth knowing.** `useParams` resolves against a **matched `<Route>`**, and a dialog route here has none — it is matched on the pathname in `App.jsx` and mounted beside `<Routes>` — so the two dialogs that take a `:userId` read the segment off the pathname instead. And **the medal catalogue could not be called `medals.js` next to `Medals.jsx`**: Windows' filesystem is case-insensitive, so `import … from './Medals'` resolved to the *data* module, which has no default export, and the dev server reported it as a missing export at `App.jsx`. It is `catalogue.js`, which is the name this project already uses for that kind of module.

**The tier pill is `LevelName` (`rC`), and its fallback is Beginner rather than `currentColor`.** Three of its four properties come off one colour by string concatenation — `<colour>1a` for the gradient's bottom stop, `<colour>99` for the border — which is why the palette has to stay in `#RRGGBB` form. `data/vipConfig.js`'s own `tierColor` helper falls through to `currentColor` instead, because the consumer that needed it does the same on the original; both are right for their call site, so this reads `TIER_COLOR` directly. It also produced **a second observed instance of the newline-name quirk**: this build's fixture is level 3, whose `levelName` is `"Bronze\nIII"`, so the family split finds no match and the pill renders "Bronze III" in the Beginner colour. That is the original's behaviour, and the capture's level-0 account reads plain "Beginner" for a different reason.

Not built, each inert at its call site: the **avatar popup** (`pt` — a `.pop-center` holding a 480px avatar over a Like button that POSTs `/game/support/system-like/like-event/`; it needs the shared popup stack), `/user/medals/item` (the single-medal detail, `Medal-DUbmmSLY.js`, recovered but not built — a tile still assembles the query it would carry), `/settings/edit-profile` behind the pencil, the **other-user pane** of Master Medals and the whole "not myself" half of the profile (nothing in this build links to another player), the reward-chest **claim** (authenticated, and its two refusal messages are recorded at the handler), the Rewards tooltip's **phone arm** (the same four lines as a pushed popup), the Wager Contest card, the `titles` name mark, and the `postMessage({type: "showProfile"})` the dialog fires at `window.top` for a native shell that a browser build has no consumer for.

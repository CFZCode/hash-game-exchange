## Wallet

`/wallet/balance` — the dropdown's first row, and the sidebar's. Built from the real chunks again: neither `index-nvcIJcIg.js` (WalletLayout) nor `index-gRxyMfB6.js` (Balance) is in the mirror, and both came off `hash.game/assets/`, along with `SelectCurrencyContent-Dr60XagM.js`, `utils-CG1cE_om.js`, `LocalAmountItem-DPF-Z1TQ.js`, `wallet-09IbmbkQ.js`, the routes profile `index-VjGkjkMa.js`, two icons and the summary card's coin PNG. Nothing on the page is read off a screenshot.

**It is a LAYOUT ROUTE, which is the original's own shape** (`{path: "/wallet", component: WalletLayout, children: [...]}`), so the rail lives in the parent and only the pane swaps. The shell around it is `fO` in the main bundle — a generic MenuPageLayout the original uses for several pages. It lived inside `pages/Wallet/index.jsx` while this was its only call site here and is now **`components/shared/MenuPageLayout`**, lifted the day `/settings` became its second; only the wide arm moved, since the two routes' narrow arms are different components on the original. See Global Settings, whose capture confirms all three of its measurements.

**The rail is nine rows because the DEPLOY says so, not because nine were counted off the capture.** The chunk declares ten and filters them through `index-VjGkjkMa.js`, a table of six white-label profiles picked by host and build flag; bc.game takes `main`, whose `routes` holds exactly balance, deposit, withdraw, buy, swap, vault, transaction, rollover, betHistory. `annualReport` is in none of the six, which is why the tenth entry never appears. **All nine are built** — Balance, Deposit (shared with the `/deposit` dialog), Withdraw, Buy Crypto, Swap, Vault Pro, Transaction, Rollover and Bet History, the last seven with their own sections below. `pages/Wallet/Placeholder.jsx` is now orphaned and is kept rather than deleted: it is the natural stub if `annualReport` ever turns up in a routes profile.

**Two different tests decide the layout and conflating them gets it wrong**: the wallet chunk's `Show when={!mobile}` is a DEVICE test (a phone gets no rail at all), while `fO`'s own `clientWidth < 1100` is a plain width test — the only 1100 in this project — that turns the 240px rail column into a horizontal strip. A desktop window at 900px is not-mobile *and* under 1100, so it gets the strip. Only the width test is expressible here and it is the one that changes the layout, so that is what the file branches on.

**Six of the nine rail icons are already in this repo and are re-exported, not copied** — the wallet chunk imports the same `IconWallet-Wtx3lbXF.js`, `IconWithdraw-DAi5-aau.js`, `IconBuycrypto-DVCGQYOc.js`, `IconTransaction-CzhZW62q.js`, `IconRollover-J2uvgr--.js` and `IconHistory-CjLCSLET.js` files the account dropdown does. That import is the one place a page reaches into a layout; move `AfterLogin/icons.jsx` to `components/shared` when a third consumer appears rather than duplicating it. Note it is a *different* set from `components/shared/icons.jsx`, which is the deposit dialog's — the two were extracted from different chunks and overlap by name only, so merge them only when a call site needs both. **Vault Pro is the exception and must not be merged**: the dropdown's is a monitor inlined in `AfterLogin-Xr01UEkM.js`, the rail's is a coin-in-a-circle inlined in `index-nvcIJcIg.js`. Same destination, two drawings.

**The wallet list is NOT the header dropdown's list, and that is the original's arrangement rather than a missed extraction.** This project's rule is to lift a component out the moment a second call site renders it, so this is the first thing to check — and it was checked rather than assumed: `SelectLayer-CwsGOFvY.js`, which `CurrencySelect.jsx` was built from, is the **same release** (Sentry `e303d2e9`) and does not import `SelectCurrencyContent` at all. The live site ships two implementations and they differ where it shows — the dropdown hovers, lights the selected row and autoscrolls to it, all off `generalAmount`; the wallet's rows are `cursor-default` with no hover or selection, off `amount`. Merging them would invent a third component that is neither. **`amount` vs `generalAmount` is the easy one to get wrong**: this page prints and sorts on the full balance, the dropdown on the withdrawable part.

Three more things the chunks settle:

- **`bg-layerx` is the chunk's and `bg-layer5` is the capture's.** The file on `hash.game` writes `bg-layerx` on the summary card — a class over a `--layerx` custom property that `index-DxOqNczA.css` only declares inside `.light-layer2-tabs`, i.e. nowhere that reaches this card. The rendered DOM says `bg-layer5` and the capture samples as layer5. The DOM wins; do not "correct" it.
- **`page-main`, `page-container` and `page-menu` are dead classes** — in no stylesheet, saved or fetched, and that was checked against the **current deploy's** `index-Cnadk-Sq.css` as well as the mirror's six. Kept like `header-nav-item`. It matters for more than tidiness: `fO` wraps both the heading and the rail in a `sticky` with no `top`, and since no rule anywhere supplies one, **the original pins neither** — they scroll away with the page.
- **A `mb-4` on the outlet container is OURS too**, on both arms of the layout. The original butts the last pane straight against the footer; this pairs with `.footer-bg`'s own 1rem, which is likewise this build's, so the visible gap is 32px. It sits on the LAYOUT rather than on a pane because all nine need it and none carries a trailing margin of its own to double up with. It was `mb-6` for one revision and read too loose.
- **The sticky rail and heading are OURS**, added on request: `top-15` (60px, the header's height) on the heading and `top-30` (120px, the heading's pinned bottom edge — 60 + 12 `pt-3` + 32 line + 16 `pb-4`) on the rail, so the rail holds directly below the heading while the pane scrolls beside it. **The heading carries no background, and that is deliberate.** A sticky heading normally needs an opaque fill, and this had `bg-layer2` — but the element is `w-full` (a full-width flex item is what forces the line break above the two columns), so the fill was an opaque band across 60..120 for the entire width and the pane's rows scrolled under it and vanished, reading as a header twice its real height. No fill is needed: the rail's natural top is already 120 so it pins from the first pixel and never enters that band, and in the pane the section title pins at the same 60 with its own `bg-layer4` and does the covering. The heading's text sits left of where the pane's column starts, so nothing passes behind the word itself. Both release at the end on their own, because sticky only holds within its containing block and both are children of the flex row; `h-fit` + `self-start` are what stop the rail stretching to the pane's height and leaving nothing to scroll against. `-mt-3` on the root cancels `--header-mb` so the heading can pin at 60 rather than 72, with `pt-3` putting the space back inside the box where its background can cover it. The Help Center made the identical departure first and is the reference.
- **The pane's sticky offsets had to be re-aimed, and the cause is a scroll-container mismatch.** `SelectCurrencyContent` pins its search row at `top-[-1px]` and its group headings at `top-14`; both are right on the original because that list sits in a **pane-local scroller**, where `top` measures the pane. This build scrolls the document — the layout clears the fixed header with padding rather than owning a scroller — so the same offsets measure the **viewport**: the search row pinned behind the 60px header, and its `z-20` painted straight over the page heading pinned at `z-10` across 60..120. That collision reads as "the right pane is not scrolling" and is not a bug in the pane. So the offsets are the call site's: the search row's pin is dropped (it was what collided, and it is not a section title) and the group headings move to `top-15` — 60px, the fixed header's own height, so a section title rests directly against the header. It shares that band with the page heading, which pins at the same 60, and the two do not fight: the heading's text sits at the far left of a `w-full` row while the title sits in the pane's column, so only their opaque backgrounds meet and the title paints on top (later in the DOM, same `z-10`). `top-30` was tried first and reads worse — it floats the title a heading's height clear of the header with its own rows already scrolled past. Each section title then holds while its own rows pass under it and is pushed off by the next, which is what the chunk intends; **that part needs no code**, since sticky holds only within its containing block and each heading already shares one wrapper with its rows. The prop **defaults to the chunk's values**, so the day this list renders inside a real scroller (the deposit dialog is one) the original's offsets are already correct.
- **`h-18` is not the `w-30` trap**: `.h-18 { height: 4.5rem }` really is in the original's stylesheet and Tailwind v4 emits the same value.

**Deposit Balance and Bonus Balance are not independent numbers** — `amount` is the sum of the other two on every wallet row, so the card's first cell is the sum of its next two. Worth knowing before "fixing" a fixture where they disagree.

**The rail icons need `icon` on them or they render solid black.** The chunk writes `class="size-5 flex-none"` with no fill and gets away with it because the icon wrapper prepends `icon`, which is `fill: currentColor` — so the glyph takes the row's text colour, `text-secondary` normally and `text-primary` on the active row. This project's icon components are the bare `<svg>` without that wrapper, so the class has to be written at the call site. It is the trap `AfterLogin/icons.jsx` warns about, and it bit here first.

**The shown fiats are BOB, TJS, INR and USD, and that list is the UNION of three captures rather than a pick between them.** Each came from a different session of the same wallet: the currency dropdown showed INR, the wallet page's rendered DOM showed BOB and TJS, and the Vault Pro page opens on USD. This file used to reconcile the first two by letting the newer win, which switched INR off; the third capture is what makes that untenable, because no single session's Cash group holds all of BOB, TJS and USD, so "which capture wins" can only ever reproduce one page's screenshot while contradicting another's. `display` is a per-row server flag a visitor toggles in Manage Assets, not a property of the account — a row being on in ANY capture is evidence it can be on — so the union is the only choice that renders every captured page correctly. The cost is a four-row Cash group where each individual capture shows one or two, and that is the right cost. **No row carries `displayStatus: 1`.** INR carried it once, on the evidence of a capture showing it survive Hide Small at zero, and that evidence is intact; it stays off because there is none for BOB, TJS or USD, and stamping one Cash row and not the other three would make the group behave inconsistently under a filter for a reason no capture explains. So turning "Hide 0 balance" on empties the Cash group, because BCD is the only row clearing ten cents — and the feature's worked example lives in the crypto group instead.

**Adding a fiat to that list only reaches the lists that read `display`.** Checked rather than assumed when USD and INR went in: the Vault transfer panel, the Balance pane and the header dropdown all grow by two, while Swap is unchanged (it intersects with `swap/config/`'s `list`, which is crypto-only), Withdraw is unchanged (`tokensFor` returns `[]` for every fiat) and Buy Crypto is unchanged (it has its own `BUY_FIATS`/`BUY_COINS` catalogues).

Verified against the fixture rather than by eye, since the browser here cannot preview: the 148-row wallet partitions 91 shown / 57 hidden, groups Cash (BOB, TJS) over Cryptocurrency (89), and the crypto order comes out **BCD, BTC, BC, SATS, ETH, DOGE** — which is the capture's own order, an independent confirmation that `groupWallet` reproduces the original's sort.

## Deposit

`/deposit` — and it is a **dialog route**, not a popup: `info.dialog = { size: [30, 44] }` (30rem × 44rem, written inline on `.dialog-list` exactly as the manager writes it), `guards: [() => !b.login && "/login/regist", () => !1]`, `titleColor: var(--layer2)`. So it renders *over* whatever page you were on, matched on the pathname in `App.jsx` like the auth dialog rather than sitting inside `<Routes>`. The first guard is reproduced — a logged-out visitor who lands on the path gets the sign-up dialog. The second returning `!1` is not a block: in that router a guard returning false means "no redirect".

**The chunk hunt is worth recording, because the entry point is a decoy.** `DialogChannelDeposit` resolves to `index-mhz6A6Ma.js`, which is only a switch across five regional channels (`kes`/`mx`/`fiat`/`us`/`jb`) falling through to a default. The actual UI is **`index-C1xohM7W.js`, 734KB** — both tabs, both selects, the QR renderer, the address block and the fiat channel grid, all in one module. The regional arms are not built; nothing here sets a channel.

**This is the first page whose DATA is mostly unrecoverable**, and that is the thing to understand before trusting anything in `pages/Deposit/deposit.js`. Every other fixture in this project is a captured response, a recovered i18n string or a live `hash.game` answer. Here the addresses, the chains a coin supports, the minimums, the fiat channels and their limits are all per-account and sit behind authentication — `api-B_IcOSNp.js` gives the real paths (they are in `endpoints.js` under `deposit`) and `hash.game` answers every one of them 6002, which was checked rather than assumed. What the fiat tab got back by other routes is the Fiat tab note below. What *is* real is marked in the file: `DEFAULT_CURRENCIES` is `eg` verbatim (`["ETH","BTC","USDT","USDC","DOGE","SOL","BNB","XRP","TON","ADA"]`, sliced `0..n` for the chips and `n..n+3` for the pile inside "More" — which is how that row was confirmed rather than read off pixels), and the address notice is its i18n string with both placeholders intact. **`n` is not a constant**: `J0` computes `const m = i ? 4 : 6` off the dialog context, so the dialog shows four chips and the wallet pane six. The pane capture shows ETH/BTC/USDT/USDC/DOGE/SOL over a three-icon stack, which is what caught it.

**The deposit address is deliberately not a plausible one.** It is the single place in this rebuild where a convincing fabrication could cost somebody real money, so `placeholderAddress()` returns something that is not a well-formed address of any chain and says what it is. Keyed on currency *and* chain only so switching either visibly changes the string and the QR, which is the behaviour being reproduced.

### The Fiat tab

**It was built from screenshots first and rewritten from the chunks and the rendered DOM later, and — as on `/deposit-offer` and `/promotions/weekly-raffle` — the diff is the useful part.** The skeleton, the six channel names and the 100–50,000 range survived. Nothing else did: the method tile is a **logo plate over a name**, not a two-line name card; the quick amounts are **generated, not listed**; the corner tag on a chip is a **background image**, not a coloured box; the 7-Day pill is a real component with four PNGs, not the emoji-on-a-gradient a screenshot suggested.

**The arithmetic is fully recovered and it reproduces the capture exactly, which is the strongest check anything on this page has had.** `lC` builds the amount ladder by walking down from the maximum in powers of ten above a floor, and that floor is the deposit **bonus's** minimum rather than the channel's — 50,000 / channel min 100 / bonus min 1,000 gives `[1000, 5000, 50000]`, which is the capture's three chips in its order. The bonus min comes from `currentUseConfigs[0].fiatRechargeV2.minDepositCurrencies.INRFIAT`, and **that is a live number**: `/activity/recharge-bonus/config/current/` is login-gated and answers 6002, but `/activity/recharge-bonus/progress/` answers unauthenticated and its seq-1 row carries the identical fields. So `services/bonus.js` assembles the config fixture out of the other endpoint's live answer — the one place in this project a fixture is built that way, and it is flagged there.

**One field in it is deliberately not the live value.** `extraBonusRatio` is 0.4 in the progress response and `null` in the fixture, because `Ni` adds the two when the second is non-null and 1.8 + 0.4 would print "+220%" on every chip — where the capture reads "+180%" with 1,000 INR showing "Extra +₹1,800.00", i.e. 1000 × 1.8. The extra ratio is a separate seasonal top-up the progress feed reports and this config does not. Note that `/deposit-offer`'s stage match and the hero's deposit slide DO add the two and print 220: three surfaces, two answers, and both are right.

**Two layouts exist and `isSmartRoute` picks.** `ID` sorts by `sort`, selects the first channel immediately and renders the grid with `hideRange` — logo over a centred name, and the amount form visible from the start. `xD` is the grouped one: categories under collapsible headings, nothing below the grid until you choose, and for INRFIAT a different tile entirely (`itemType: "col"`, a wide row with an `h-12 w-20 sm:w-32` plate, capped at three behind a View more/less). The rendered DOM shows six tiles *and* the amount form, so it is `ID`; the grouped arm is not built.

**The rendered markup is what settled the fixture**, and it settles more than a screenshot could: all six channel logo URLs, that the **sixth row is under maintenance** (it is the only tile carrying the `bg-black_alpha20` mask and the slashed eye), that the tiles show neither a range nor an ETA, that **no channel offers a how-to guide**, and that the submit reads "Deposit Via UPI" with a link mark. It also corrected `IconInform`'s path — the drawing in `Dn`'s notice box is not the one this file had — and supplied `.absolute-center`, which was missing from `index.css`.

**The channel logos ARE local now.** Six rows, two distinct CDN paths for the UPI mark, **four files** — `img2.distributedresourcestorage.com/fait/…`, the same host the raffle avatars came off, and the URLs exist nowhere but that rendered DOM. `utils/channelArt.js` is the glob; `nightIcon` doubles as the basename, the arrangement `promotions.js`'s `image` uses. `lightIcon` is deliberately not fetched, since `b` in `utils-BRLjIBPE.js` picks on the theme and this build is dark-only.

**`SevenDayPayBanner-BD56xym6.js` has two banners and the fiat page takes the small one.** `S` is the full-width card with the coin and two stars; `a` is the 24px pill, which is what `xw` renders `class="ml-auto mt-3"`. The card's artwork is fetched and sitting in `assets/deposit/` anyway, unused, for the day the slot is filled. Clicking the pill opens the Trust & Compensation explainer, whose copy is verbatim i18n — including a live bug kept as written: the chunk interpolates the **empty string** for `currencyName`, so the second guarantee really does read "If your  deposit hasn't arrived", double space included.

**`HowToDeposit.jsx` renders nothing today and is kept anyway.** Its six guide templates are verbatim i18n out of `HowToDepositFiat-UEEoyF-D.js` and its gate is the original's; no channel in this fixture carries a guide, which the rendered DOM confirms by having no link between the grid and the form. What this build could never supply is the media — `guideUrl` is a per-locale PDF map and `guideVideoUrl` a video, both arriving with the authenticated channel payload. `step-box` and `a-step` are dead classes in the current deploy's stylesheet as well as the mirror's, and are kept.

Two more things reproduced rather than tidied: the chip's label is a **`<button>` nested inside a `<button>`** on the original (a `<span>` here, which renders identically under preflight), and the amount block sits in `E1`'s **`<form>`** — which holds only the amount here, since no channel asks for KYC fields, but is what makes Enter in the box submit.

Not built at all: the recent-wallet strip and the whole KYC/registration/iframe-checkout branch under the fiat submit — which is why that button is inert.

**Live builds draw no channel grid; the INR tab is this build's Manual / Automatic pair** (user's request, 2026-10-24). Manual is `ManualDeposit.jsx` (house bank account, UTR + screenshot, staff approve). Automatic is `AutoDeposit.jsx`: a "Pay With" row of F2Pay's methods in the selected currency (UPI for INR; QRIS, DANA, CIMB, BRI, MANDIRI, BNI for IDR — paid and credited in that currency, no conversion), the amount, then `POST /user/payments/deposits` with `provider: 'f2pay'` and the `method` → the browser goes to F2Pay's cashier page (`redirectUrl`), and F2Pay's signed callback credits the wallet. FiatTab shows a two-button "Deposit Method" row (ManualDeposit's own `button-brand` / `button-second` pair) only when both are open: manual by `gates.manualDeposit()`, automatic by `gates.autoDeposit()` plus `GET /user/payments/methods/f2pay` answering a non-empty `[{ method, currency }]` (the `payment_methods` rows both the owner and the Super Admin have on) (owner flag `gateway_f2pay` and the Super Admin's Payment Methods switch both on, keys in backend/.env). With one open, that one shows without the row.

**THE DIALOG IS ONLY THE SHELL, and that split is the router's, not a convenience.** `index.jsx` is portal, scrim, title bar, scroll lock and Escape; everything inside the scroller lives in `Panels.jsx`, because **the same component is mounted by two routes** — `/deposit`, which carries `info.dialog`, and `/wallet/deposit`, which does not and renders as a pane in the wallet layout. What differs between them is not a prop and not a second component but `Go()`, the router's own dialog context: `h3.Provider` is installed only when `route.type === Le.DIALOG`, so a dialog reads a value and a page reads `undefined`. `src/context/dialogRoute.js` carries the proof and the places the original branches on it — the tab strip (sticky, `-mx-4`, `type="indicator"` vs a bare strip with filled tabs), the quick-pick row (`i ? 4 : 6` chips), `PageLayout`'s card (`!isDialog && "lg:px-8"`), the Cwallet row's extra `mt-4`, and `w3`, which turns a page's title into a dialog's title bar and nothing at all. It lived at `pages/Deposit/dialogContext.js` until the withdraw pane became its second consumer; it was never the deposit page's own. That is also what finally replaced the wallet rail's Deposit placeholder.

**The Cwallet row is built** (`Sn`/`xn` in `Banner-TuTj1pp2.js`), with the `zr` rule/or/rule divider above it. Its `h-[.5px]` alongside `border-t-[0.5px]` is the original's own belt-and-braces — the border draws the line, the height stops the `<hr>`'s box rounding up to 1px. **It is gated on a payload this build does not have and renders anyway**: `Sn` shows it only when `cwallet.state.supported && !cwallet.state.cwalletId`, and there is no cwallet response and no endpoint answering for one, so there is nothing to gate on and the capture shows the row. Wrap it the day that feed exists rather than inventing a flag now. The logo is the deploy's own `cwallet-CIDMlLxn.png`; its light-theme twin is deliberately not fetched, since a dark-only build can never reach that arm.

`qrcode` is the one npm dependency this project has added. It stands in for the encoder bundled into `QrCodeImg-BMVeZCYd.js`; `QrCode.jsx` draws to a **canvas** rather than an `<img>` so the coin mark can be punched into the finished modules in a second pass, which cannot drift out of alignment the way an absolutely-positioned overlay can.

**Note the tab strip's `[&_.tabs-btn-group]:px-4` where Manage Assets uses `px-6`.** The indicator's two custom properties have to be computed off *that* number, and the two panels genuinely differ — see the `GROUP_PADDING` note in `ManageAssets.jsx` for why the width and the offset resolve their percentages against different boxes.

**Four measurements that a first pass got wrong, each settled by the source rather than by the pixels:**

- **`class` on a `TabItem` belongs to the CONTENT panel, not to the button.** `G(Yc.TabItem, {class: "flex-auto bg-transparent", title, children})` passes it through to the pane. Put on the button it replaces `.tabs-btn`'s `flex: 1` with `flex: 1 1 auto`, which sizes each tab from its LABEL — "Crypto" is wider than "Fiat", so the split slides right and both labels sit off centre. That is the whole of a "the tab text has moved right" symptom.
- **The dialog's close is `.dialog-close`, not `.pop-close`**, and the difference is position. `.pop-close` pins itself to `top: .75rem`; `.dialog-close` carries no position at all and the markup wraps it in `ml-auto absolute right-4 top-0 flex items-center h-full`, so it centres against the title bar's **full** height. Using the `.pop-*` one puts the cross a few pixels high.
- **The Currency select's layer is `min-h-[80vh] w-100 sm:min-h-100`** (`zn` in `Banner-TuTj1pp2.js`) — 400px wide with a 400px floor from `sm` up, not `.dropdown-layer`'s default 18rem. Both beat that rule's own `max-height: 20rem` the same way `.currency-select` does: a min-height wins against a max-height. Its contents are `SelectCurrencyContent`, a sticky search bar over coin rows, which is why `Select` gained the `layerRender` hook `MultiSelect` already had.
- **The notice box is `p-2 rounded-xl`, not `p-3 rounded-lg`** (`UA` in index-BsFv7ByC.js), with the mark carrying its own `-mt-0.5 size-6 mr-1.5 fill-success` rather than the row using a gap. Four extra pixels a side is what made it read as over-padded.

**Three rules were missing from the shared `.dialog-*` shell** and are now transcribed: `.dialog-content`'s `padding-inline: 1rem` (only `flex: 1` had been copied, which is why this dialog first wrote its own `px-4`), `.dialog-content > .scroll-container`'s `padding-bottom: 1rem`, and `.dialog-title` / `.dialog-close` themselves. Safe to add — the one existing consumer is the auth dialog, which carries `dialog-transparent-title` and so already zeroes both sides at higher specificity.

Two more shared primitives were filled in for this page. **`.button-input` had been named but never defined** — `.button:hover:not(:disabled, .button-input)` has been sitting in `index.css` excluding a class that generated nothing; it is one of the four button *types* (`zx` maps `{brand, second, input, cashout}`) and is the filled square a Select puts its chevron in. And `--color-warning` (#FF9820, `.app-root.dark`'s own) was added for the "not supported in this currency" notice.

## Withdraw

`/wallet/withdraw` — the crypto withdraw form, and the second wallet pane built. Same shape as deposit: `DialogWithdraw` mounts at `/withdraw` (a dialog, in the group `{dialog: !0, guards: [ce]}`) and at `/wallet/withdraw` (`info.dialog = mobile`, a DEVICE test that is false on desktop). **Both arms are built now** — `WithdrawPanels` was split out of a shell it did not yet have, and `Withdraw/Dialog.jsx` is that shell: three lines over `components/shared/RouteDialog` plus the `DialogRouteContext` provider, mounted from `App.jsx` below `lg`. The title comes from the mount rather than from the panel, because `PageLayout title="Withdraw"` pushes its string into the router's dialog context and this project's port of that context carries the flag and not the string.

**The INR (fiat) arm is this build's Manual / Automatic pair** (user's request, 2026-10-27), the deposit tab's twin. Manual is the staff-reviewed form (`ManualWithdraw` in `FiatForm.jsx`). Automatic (`AutoWithdraw`, same file) takes Account Holder Name, Account Number, IFSC and the amount and `POST /user/payments/withdrawals` with `provider: 'f2pay'`, `details: { account_name, account_number, bank_code }` — the balance is held at once, F2Pay pays BANK_INR, and its signed payout callback marks it paid or refunds it. The two-button "Withdraw Type" row shows only when both are open: manual by `gates.manualWithdraw()`, automatic by `GET /user/payments/methods/f2pay` answering `payout: ['INR']` (backend AUTO_WITHDRAWALS_ENABLED, owner `withdrawal_mode`, `gateway_f2pay` + `f2pay_inr`, Super Admin's F2Pay switch).

**The rest of `/wallet/*` still does not do this.** The wallet LAYOUT carries the same `info.dialog = m.mobile`, so on the original every pane is a full-screen dialog on a phone and the rail never renders there at all; here only Withdraw is lifted, because it is what the mobile account page's own button reaches. Each of the others wants the identical three-line file. The route's own guard, `Pe.isFiat && !H.bcmx && "/deposit?type=withdraw"`, never fires on this deploy.

**`--layer0` is not a fifth layer, it is "whatever layer I am sitting on".** `index-DxOqNczA.css` declares it at layer4 on the theme root and then re-declares it *on the utilities themselves* — `.bg-layer3 { --layer0: rgb(var(--layer3)) }` and so on for 2/4/5 — so painting a box publishes its fill to its descendants and a child written `bg-layer0` matches without naming a colour. **Deliberately not ported:** `ht` carries an obfuscated anti-tamper snippet — a `TextDecoder` over hex-XOR'd bytes comparing `document.domain`, fired on a 27-second timer. It is anti-tampering, not UI.

**This page is what exposed the dropdown-placement bug, and the real rule is now in `Select/position.js`.** `js` in index-BsFv7ByC.js places a layer with `d.x + p.width < innerWidth ? d.x : Math.max(0, d.x - p.width + f.clientWidth)` — it **flips sides**, start-aligning to the trigger when the layer fits and END-aligning (right edges flush) when it does not. This build clamped the left edge into the viewport instead, which is a different thing, and the two only diverge for a trigger that is both narrow and far right: the transfer panel's coin pill is ~110px at the right end of a ~450px card, so an 18rem layer overhung the card by ~180px and the clamp dropped it under neither. The layer's width is **measured** now rather than assumed at 18rem, since the end-align branch subtracts it and two call sites override it by class. Two further parts of `js` are recorded there as deliberately unported — the inline `width: max(layer, trigger)` and the shrink-to-fit height clamp — because neither changes anything today and both would override class-set sizes on three verified pages.

**One departure from the chunk, and it is the font set rather than taste:** the Total Value symbol is `font-semibold` where the template says `font-bold`. This project ships Averta at **400/600/800 only**, and CSS font matching for a desired weight above 500 searches weights `>= desired` **ascending first** — so `font-bold` (700) resolves to the **800 ExtraBold** face, the very same one the digits beside it get from `font-extrabold`. Symbol and number came out at identical weight, where the original has a real 700 against an 800 and the symbol reads a step lighter. 600 is the only step below that exists here, so it is the honest stand-in for a 700 this build cannot render. **This generalises: every `font-bold` in the project is silently rendering ExtraBold**, which is the same trap as the missing rupee glyph at 800 — see the note on the bare `font-family` declaration under Styling. Colour is unchanged; both symbol spans are the chunk's own `text-primary`.

Nothing was invented to reach it and nothing is read off the screenshot.

**Only one path is new.** The other four lists are the history feeds of the panes that write them, so they already sat under `deposit`, `withdraw`, `swap` and `buyCrypto` in `endpoints.js` rather than being duplicated into a `transaction` group.

**The filter state is persisted, and where it comes from is the useful part.** Each key is read from the SEARCH PARAMS first, then `sessionStorage` under `wallet:tx-filter-v2`, then the defaults — and the whole set is written back on every change. Two consequences: the Vault card's History button works (`/wallet/transaction?type=bill&billType=Vault` lands with the Bill Type filter already set, verified), and the pane remembers your filters for the tab's lifetime but not beyond it. Session, not local — the original picked the storage that forgets. Seeded **once**, at provider mount, so editing the URL afterwards does not re-seed; `useState` initialisers reproduce that exactly.

Five things the chunks settle:

- **Three of the five filters are conditional, and the grid is what makes that read well.** Bill Type renders only for Bill, Status only for Deposit and Withdraw. The strip is `grid grid-cols-2 sm:grid-cols-3`, so the four visible on Bill wrap 3 + 1 — which is the capture.
- **Changing type clears `status` and `billType`.** Without it a Bill Type of "Vault" would silently narrow the Deposit list.
- **Bonus has no list of its own.** `Ye` has no branch for it; it falls through to the Bill table with `changeTypeName` pinned to `"Bonus"`. Easy to mistake for an omission.
- **The time range is ONE STRING**, either `preset:<ms>` or `<start>-<end>`, which is what lets it live in sessionStorage and in the URL as a scalar. Deposit and Withdraw cap at 60 days where everything else allows 90, so the 90-day preset disappears for those two — and a range at 60 days or more on either of them raises the pane's own "only the last 2 months are available" notice. `timeRange-Chxugo4p.js` is ported whole into `services/transaction.js`, including the extra day of slack its clamp allows.
- **The header row is `bg-layer2` inside a `bg-layer4` card** — darker than the surface it sits on, which reads as inverted until you notice the card is the lighter one here. The shell's own pair is `isDialog ? "bg-layer3" : "bg-layer2"`; this pane is only ever a page on a desktop.

**`IconInform` is TWO DIFFERENT DRAWINGS under one name, and this pane picked the wrong one first.** `IconInform-Dfks8fNQ.js` — what the chunk imports, a squircle outline around a dot and stem — lives in `AfterLogin/icons.jsx`; the `IconInform` in `components/shared/icons.jsx` is the deposit dialog's filled circle. The two icon sets were extracted from different chunks and the head of that file already warns that a few glyphs share a name and not a drawing (Vault Pro is the documented case). Add a third: check which chunk a page imports before reaching for the nearer module.

**"Stay tuned…" is spelled two different ways in the bundle and both are correct.** `ks`, the empty-state section, uses a plain hyphen; `W3`, the Select layer's no-results state, uses an em dash. Checked by codepoint (45 against 8212) after the two looked like a typo. `components/shared/EmptyPlaceholder` and `components/shared/Select` differ accordingly; do not normalise them.

**THE DEPOSIT AND WITHDRAW ROWS ARE BUILT** — `me` in `index-BnY4Y-60.js` and `Re` in the pane's own chunk, with their status machines in `Transaction/status.js`. They are NOT one component with a prop, and the differences are the chunks': a deposit prints `isSuccess ? receiveAmount : amount` where a withdrawal prints one figure; the signs are opposite and asymmetric (deposit is `+`/success at both widths, withdraw is `-`/error on a desktop and `auto`/`auto` on a phone, so a refund reads as a credit there); a deposit's anchor sits INSIDE a `border-b border-third` div so the UTR line can share the rule, where a withdrawal's anchor carries the border itself; and their status cells differ by exactly one class, `text-secondary` on withdraw and not on deposit. **The two status machines are the SOURCE of this pane's status vocabulary**, which is why the platform's normalised WORD is turned into the bc.game CODE that already means it rather than rendered directly — see the adapter's note. Both rows link to `/wallet/<type>-detail?orderId=…`, which is not a route here, and the href is left as the chunk's for the reason the bet-history row's is. Not rendered, and both correctly: the fiat UTR-verify line (gated on `mode`) and the support-ticket chip (gated on `ticketId`) — the platform sends neither field. Still not built: Swap and Buy Crypto's row renderers (neither feed answers on either backend), the Bill row's game-detail link and copy button (both behind authenticated calls), the custom date range behind the Time filter's "Custom" entry (only the presets are built, which is what the capture shows and what the filter actually stores), and the infinite pager, which has nothing to page.

## Rollover

`/wallet/rollover` — the wagering-requirement ledger: every bonus with a rollover attached and how much of it is still to be wagered. `DialogTurnover` resolves to `index-N228sAQi.js` (5 KB) over `Details-DZ3wUplM.js` (13.5 KB — the API namespace, four enums, the status badge and the detail dialog). Both off `hash.game/assets/`. **`DialogTurnover2` resolves to the same chunk**; only `DialogTurnover` is routed.

**It reuses three of the transaction pane's own files, which is what triggered the extraction.** `index-DP7RdwkJ.js` (the card shell), `CurrencyAmount-CcsyxXsB.js` (the filter store *and* the amount cell) and `Table-Cyxc_MMr.js` are the same modules on the original, so they moved out of `/wallet/transaction` and into `context/WalletFilterProvider.jsx` + `context/walletFilter.js`, `components/shared/Table` and `components/shared/CurrencyAmount`. The transaction pane's rendered markup was diffed before and after and is byte-identical. The context/hook split is the `SessionContext.jsx` + `session.js` rule again — `react-refresh` rejects one module exporting both.

**Another empty state, and `types` is the probe worth recording.** All four endpoints answer 6002 — including `/balance-controller/wager/task/types/`, which was worth checking rather than assuming, because a list of bonus categories looks exactly like the catalogues the `game/support` family has now handed out four times (`usdPrice`, `index/minimal`, `currencyTokens`, `swap/config`). It is not one: the types are scoped to the account's own tasks. So the Bonus Type filter keeps its seeded first entry, which is what the original shows until that fetch lands, and the list renders the site's empty state. That is the capture.

Four things the chunks settle:

- **The Bonus Type filter renders only when Type is Bonus**, which is why the capture shows two controls in a three-column grid rather than three. Its options are **seeded and appended to**, not replaced: the store starts at `[{label: "Bonus Type", value: 0}]` and the fetched rows are pushed after it, so that label is a placeholder that becomes the "all" option once data arrives.
- **The filter values are numbers held as strings**, with `""` for unset — deliberate rather than sloppy: `0` is the `AllStatus` enum member, so an empty string is the only way to express "no status filter" and have the request body drop the key.
- **`Type` and `TaskType` are different scales that both read as "type".** `Type` is the filter's axis (All 0 / Deposit 1 / Bonus 2); `TaskType` is the row's (DepositBonus 3 / SpecialDepositBonus 11). `A(isBuy, taskType, taskTypeDesc)` reads the second and compares against a bare `1` that is in neither enum — left as the literal rather than dressed up as a lookup it does not belong to. Both call sites in this chunk pass `false` for `isBuy`, so that arm is unreachable.
- **`Status.Cancelled` covers two renderings.** Status 4 prints "Canceled" normally and "Fully Used" when the row's `remark` is `cancel_by_system`; the filter offers them as one option, "Canceled/Fully Used". The status colour is applied to a **dot**, not the label — `D` in `Image-D1QE7fNY.js` is an `<svg fill=currentColor>` holding one 8-radius circle, which is why a `text-*` class colours it.

**`.status` on the badge's label is a dead class** — nothing in the mirror's six stylesheets nor the current deploy's `index-DGr5jguQ.css`, both checked. Kept, like `header-nav-item` and `page-container`.

Not built: the row detail (`/wallet/roll-detail?taskId=…`, the larger half of `Details-DZ3wUplM.js` — progress bars, a cancel action, a help popover — and it needs a `detail` response), the mobile two-column arm, and the pager.

## Bet History

`/wallet/bet-history` — the ninth and last wallet pane, and the cheapest of them: `DialogBetHistory` resolves to `index-D5N4LJZ-.js` (6.4 KB) and that one file is the whole page. Every other module it needs is one this project already had, which is what nine panes of extraction buys.

**TWO ENDPOINTS FOR ONE LIST, AND IT IS CURSOR PAGING RATHER THAN A SECOND FEED.** Page 1 posts to `bet-history-first/`; every page after it posts to `bet-history/` with the same filters plus the `minDistributeId` the previous response handed back. So the list is keyed on a cursor, not an offset — a bet placed while you are reading page 3 cannot shift page 4 under you, which an offset would.

**Both answer 403, and it is a different 403 from the transaction pane's.** This one is `{"msg":"Request 403 error.","code":4001}` — bc.game's own envelope with an application code — where `/user/amount/change/record/` returns a Spring error page. Worth noting only because it means the rejection is deliberate rather than a gateway rule. Either way the list is empty and the pane renders the site's own empty state, which is the capture.

Three things the chunk settles:

- **Payout is a MULTIPLIER stored ×10000.** The cell is `payout / 1e4` with a literal `x` after it, so a 2.5× bet arrives as `25000`. Print it raw and every row reads as a jackpot.
- **The row is always an anchor, even when it does not link.** Only Original, Live and Slots (types 1, 3, 5) have a `/game-detail/<distributeId>` to open; the rest keep the `<a>` and take `pointer-events-none`. The same test decides whether the little arrow shows at the end of the Profit cell — so the arrow *is* the affordance, and its absence is the whole visual difference between a live row and a dead one. Note `/game-detail/:id` is not a route in this build, so a linkable row falls through to the catch-all; the href is left as the original's, since the path is right and only the page is missing.
- **The Type filter spans two grid columns below `sm`** (`col-span-2 sm:col-auto`), the only wallet filter that does. With three controls in a 2-column grid it would otherwise sit alone on the second row; spanning puts it on its own first row and pairs the other two. Its eight values also have a **gap at 2** — "" then 1, 3, 4, 5, 6, 7, 8 — so whatever category 2 was has been retired from the filter with the numbering left alone.

**The list's own truncation is ported even though nothing can reach it**, because it is the kind of thing that is wrong for a long time before anyone notices: page one caps at 50 rows and later pages at 500, rows with no `time` are dropped, and **overflowing the cap is what keeps paging alive** (`noMore` becomes `Infinity` when there is more and the current page number when there is not). The `!!time` filter runs before the slice but the cap test runs on the *unfiltered* length, so a page of 51 rows where two lack timestamps yields 49 and still reports more. That is the original's own edge.

**`AssetsFilter` and `TimeFilter` moved to `components/shared/WalletFilters` for this page** — `Assets-NsyfBPnl.js` and `Time-Biy5hfP-.js`, two chunks on the original, one module here because they are always imported together and neither has a call site that wants one alone. The transaction pane's markup was diffed before and after and is byte-identical. **The Time filter's 60-day cap is portable by accident and it is worth knowing why:** it tests `type === "withdraw" || type === "deposit"` on the literal strings, and the three panes store completely different things in `type` (transaction: `"bill"`/`"withdraw"`/…; bet history: `""`/`"1"`…`"8"`; rollover: `"0"`…`"2"`, with no time filter at all). Only the first can ever match, so only the first is ever capped — with nothing passed in. Do not "fix" that comparison to use an enum.

Not built: the `center` slot between the filters and the table (`ProviderBalanceList`, a lazily-resolved component listing unsettled balances held with game providers — it needs `/platform-japarot/user-provider-balance-list/`, the same feed the currency dropdown's unsettled-bets banner is blocked on, and it renders nothing in the capture either) and the pager.



## `/wallet/deposit-detail` — the link every deposit row already had

`DialogTransactionDepositDetail` in the route registry, and the destination the Transaction pane's
deposit rows have linked to since they were built. The note there said the route "is not built
here, so they fall to [Home]". It is built now.

**It is not a port of the original's screen, and the reason is the model.** bc.game's is
`index-BFEy-_b7.js` (recovered off `hash.game/assets/`, not in the mirror) and it is written for
their PAYMENT-ORDER object — its own call is `/payment/order/apply/delay/bonus/`, a channel order a
provider is processing with a delay-bonus offer attached. The platform has no such thing. A fiat
deposit here is a **manual bank transfer**: the player declares one with a bank reference and a
proof image, and staff approve or reject it with a comment. Filling a payment-order layout with a
bank-transfer record would be the mistake `services/kyc.js` argues against at length, so the screen
is small and this build's.

**What makes it worth building is one field.** `/user/history/deposits` — which is what the pane
lists — merges seven tables into `{id, reference, amount, currency, status, details, date, kind,
method, type}`. It carries neither the screenshot nor **`adminComment`, the only place a rejection
is explained.** A player could see that a deposit was rejected and never learn why.

### Two ids, and they are not the same id

The row's link is the original's: `?orderId=…`, where `orderId` is `reference ?? id` — for a manual
deposit that is the BANK REFERENCE (`DEMO-REF-0001`), not a number. `/user/deposits/fiat/:depositId`
wants the numeric id, and no route looks a deposit up by reference, so the list is read and matched
on `transactionId` (the same field the merged history exposes as `reference`), with a fallback to
`depositId` for a row that had no reference of its own.

The screenshot is authenticated, so it is fetched as a Blob and turned into an object URL the
dialog revokes on unmount — the same handling, and the same reason, as the KYC document.

**A crypto row lands here too**, since the pane links every deposit the same way and this is the
only detail read there is. It gets the not-found state rather than a wrong one, which is honest
until `/user/history/crypto/deposits` has a detail route of its own. `/wallet/withdraw-detail` is
the same shape and is NOT built, for the same reason: nothing would fill it.

Verified through the real path — Type filter to Deposit, time filter widened past the pane's
"Past 24 hours" default (the seeded deposit is older than that, the same expiry the bet-history
harness lines hit), the row appears, and clicking it opens the detail with the reference, bank,
UPI id, status and the proof image loaded from its blob.

## `/wallet/withdraw-detail` — the deposit detail's sibling

`DialogTransactionWithDrawDetail`, the second of the two links the Transaction pane has always
carried and the second that fell through to Home. Like the deposit detail it is not a port —
bc.game's is written for their payment-order model — and here it has a further problem the deposit
side does not: **there is no single withdrawal object.** `withdrawals` is the crypto table and
`fiat_withdrawals` the manual one, with different columns, different services and different
presented shapes, merged only for the list.

### `rail` is this build's parameter, and it is forced

The two tables have **independent id sequences**, and `/user/history/withdrawals` merges them keyed
on `id` with `reference` null on both — so `orderId` IS that id, and two rows in one list can carry
the same one. Confirmed by seeding the collision: a crypto withdrawal at `id=2` and a fiat one at
`id=2` in the same response, where `?orderId=2` alone cannot say which is meant. The row appends
`&rail=` from the merged row's own `method`; a link arriving without one reads as fiat, so a
hand-typed URL resolves rather than errors.

### What each rail will and will not show

| | fiat | crypto |
| --- | --- | --- |
| shown | holder, bank, UPI id, amount, status, requested | amount, coin, chain, masked address, txid, status, date |
| withheld | `accountNumber`, `ifscCode` (`forStaff`) | full address (masked to `0x1234…5678`), `note`, `decidedBy`, `decidedAt` |

**So a rejected crypto withdrawal cannot be explained to the player** — its `note` is staff-only,
where a rejected fiat DEPOSIT explains itself through `adminComment`. The dialog says the reason is
not shown rather than leaving a blank under a rejected status, and `docs/backend-gaps.md` gap 26 asks
for the field. That note also records the third disagreement found here: the merged history hands
the player `accountNumber` and `ifscCode` that the fiat rail's own service withholds.

Verified through the real path on both rails and on a forced id collision — the crypto row resolves
to BTC/BEP20 with its masked address and the not-shown-reason line, the fiat row to the bank and
UPI id, and `orderId=2` resolves differently under each rail. All seeded rows were removed
afterwards; the only withdrawal left is the delivery's own, on the demo staff account.
